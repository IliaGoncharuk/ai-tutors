# День 12 — персонализация ассистента

## Исходное задание

🔥 День 12. Персонализация ассистента

Добавьте персонализацию поверх модели памяти:

👉 создайте профиль пользователя

👉 опишите предпочтения (стиль, формат, ограничения)

👉 подключите профиль к каждому запросу

Проверьте:

👉 ответы для разных профилей

👉 что ассистент учитывает автоматически

Результат:

Персонализированный агент, адаптированный под пользователя

## Теория

**Персонализация** — изменение способа ответа с учётом конкретного человека.
Она может определять сложность объяснения, тон, объём, формат и нежелательные
элементы ответа. **Профиль** — сохранённое описание таких предпочтений.
Это не переписка целиком и не набор фактов о текущей задаче: предпочтение
«объяснять термины» может пригодиться в разных разговорах, а срок одного
проекта обычно относится только к этому проекту.

| Вид предпочтения | На что влияет | Нейтральный пример |
| --- | --- | --- |
| Уровень подготовки | Нужны ли определения и промежуточные пояснения | Объяснить проценты без предположения о знании формул |
| Стиль | Тон и плотность изложения | Спокойное подробное объяснение |
| Формат | Организация материала | Нумерованные шаги вместо большого абзаца |
| Ограничения ответа | Что желательно исключить или ограничить | Без эмодзи, до пяти пунктов |

Один вопрос «Как работает сложный процент?» можно раскрыть через пример
накоплений для начинающего или через формулу и допущения для подготовленного
читателя. Смысл и исходные числа должны сохраняться; меняется подача.
Это позволяет отличить полезную адаптацию от простого обращения по имени.

Профиль начинает влиять на ответ только после включения в контекст модели.
Поэтому приложение должно явно подставлять актуальные предпочтения при
обращении к ней, а не рассчитывать на случайное упоминание в старом диалоге.
В Responses API инструкции относятся к текущему запросу; их передача
и приоритет описаны в
[официальной документации](https://developers.openai.com/api/docs/guides/prompt-engineering#message-roles-and-instruction-following).

Предпочтения полезно отличать от обязательных правил. Просьба «в этот раз
объясни подробнее» может уточнить обычное предпочтение краткости. Требование
сохранности данных или запрет операции имеет другое назначение: удобный стиль
ответа не должен его отменять. Также нельзя считать предположения о человеке
проверенными сведениями — профиль должен быть доступен для просмотра и правки.

Для проверки персонализации нужны одинаковые вопрос и факты при разных
профилях. Если одновременно менять историю, задачу и предпочтения, различия
ответов нельзя уверенно приписать профилю. Проверяют отдельно наличие профиля
в запросе и то, насколько ответ соответствует ему. Одного удачного ответа
недостаточно, чтобы считать следование предпочтениям гарантированным.

## Решение

**Замысел.** Создать локального помощника для обсуждения проекта, у которого
пользователь выбирает и редактирует профиль. Ассистент должен автоматически
подставлять предпочтения в каждый вопрос, чтобы человеку не приходилось
повторять «объясняй проще» или «ответь списком». В отдельном сравнении один
вопрос получает три ответа с разной подачей при одинаковых исходных фактах.

**Устройство.** Самостоятельный сайт на React и TypeScript с сервером Node.js
содержит чат, три слоя памяти и редактор профиля. Доступны профили `novice`
(начинающий), `expert` (разработчик) и `manager` (руководитель). В каждом задаются
уровень подготовки, стиль, формат и ограничения ответа. Их можно менять
через интерфейс; профиль применяется автоматически даже при отключении
слоёв памяти в просмотре контекста.

Диалоги, задачи и личные записи связаны с выбранным профилем. Переключение
профиля не подмешивает чужую переписку и память. Сравнение профилей работает
иначе: оно сохраняет факты активной задачи и её долговременные сведения,
убирает короткий диалог и меняет только предпочтения. Это сравнение подачи
одних данных, а не объединение персональной памяти. Ответы сравнения
не записываются в диалог.

Состояние хранится вне репозитория в `~/.ai-tutors/memory-lab-day-12/`;
профили находятся в `long-term.json`, переписка и задачи — в отдельных файлах.
Сайт восстанавливает опубликованный снимок после перезапуска. Подробные
правила — в [спецификации](../../docs/features/day-12-personalization.md).

Нужен Node.js 22.13 или новее. Команды из корня репозитория устанавливают
зависимости и запускают сайт на [localhost:3012](http://localhost:3012):

```powershell
npm.cmd --prefix challenges/day-12-personalization ci
npm.cmd --prefix challenges/day-12-personalization start
```

По умолчанию используется OpenAI и `gpt-5.6-luna`. Ключ берётся из серверной
переменной `OPENAI_API_KEY`; каждый запрос отправляет модели включённые данные
и расходует API-токены. Для знакомства без API предусмотрена явно помеченная
симуляция. Просмотр контекста позволяет увидеть передаваемый профиль.

Первая команда ниже выполняет локальные тесты, проверку типов и сборку без
платного API. Вторая выполняет три реальных запроса сравнения профилей:

```powershell
npm.cmd --prefix challenges/day-12-personalization run check
npm.cmd --prefix challenges/day-12-personalization run experiment:live
```

## Результаты и выводы

20 сентября 2026 года выполнены **3 реальных запроса к GPT-5.6 Luna**:
1798 входных + 1488 выходных = **3286 токенов**. Вопрос:
«Предложи, как организовать отмену занятия и избежать двойного бронирования
в нашем сервисе. Дай практический следующий шаг».

Для всех вариантов использованы одинаковые вымышленные факты: сервис записи
к репетиторам, занятие 45 минут, веб-приложение, русский язык
и `Asia/Yekaterinburg`. Краткосрочный диалог исключён; менялся только профиль.
Точные предпочтения, записи и API-входы — в [JSON-протоколе](results/live/results.json),
все ответы — в [отчёте](results/live/report.md), автоматические проверки —
в [исполнителе эксперимента](scripts/experiment.mjs).

| Профиль | Запрошенная подача | Наблюдаемый ответ |
| --- | --- | --- |
| Начинающий | Простые короткие абзацы, объяснение терминов и один бытовой пример | Объяснил, что такое сервер, показал пересечение занятий 10:00–10:45 и 10:30–11:15; основной ответ оформил длинными списками |
| Разработчик | Три кратких технических пункта с рисками | Три раздела про отмену, защиту от двойной записи и следующий шаг; названы транзакция, индекс, повторные запросы и гонки |
| Руководитель | Таблица «решение — польза — риск», без кода, с критерием успеха | Таблица из шести решений, отдельные критерии успеха и четыре сценария проверки |

Простые признаки формата сработали **3/3**: слово, обозначающее пример,
три нумерованных пункта и строка таблицы. Это не оценка полного соответствия
профилю. В ответе начинающему пример относится к самому сервису, а не к бытовой
аналогии, и остаётся необъяснённый термин «слот»; пожелание коротких абзацев
тоже выполнено лишь частично. Проверка отсутствия блоков кода не обнаружила
таких блоков, но не доказывает соблюдение всех ограничений.

Подача заметно меняется без повторения предпочтений в вопросе. При этом
предложенные условия отмены различаются: в примерах фигурируют 12 часов,
24 часа и начало занятия. Они не были заданными фактами и требуют решения
владельца сервиса. Персонализация не превращает рекомендации в принятые правила.
Один ответ на профиль не доказывает устойчивость адаптации; корректность
архитектуры и полнота бизнес-правил этими признаками не измеряются.
Повторная команда эксперимента заменяет файлы `results/live/`.

Прошли 30 локальных тестов, проверка TypeScript и сборка. В браузере проверены
сравнение трёх профилей в симуляции, пустая память при первом переключении
профиля, изменение формата ответа и его сохранность после перезагрузки.
Ограничения в профиле остаются предпочтениями подачи: эта версия не реализует
запрет операций через обязательные инварианты.

## Практическая польза

Персонализация помогает одному ассистенту объяснять материал людям с разной
подготовкой и учитывать устойчивые пожелания без повторного ввода.
Раздельная память профилей сохраняет границы их задач, а контролируемое
сравнение позволяет увидеть, изменился ли ответ по существу для читателя.
