# День 15 — контролируемые переходы состояний

## Исходное задание

🔥 День 15. Контролируемые переходы состояний

Реализуйте явные переходы между состояниями задачи.

Сделайте так, чтобы:

👉 у задачи были допустимые состояния

👉 были разрешённые переходы между ними

👉 ассистент не мог “перепрыгнуть” этап

Пример:

👉 нельзя делать реализацию до утверждённого плана

👉 нельзя делать финал без валидации

Проверьте:

👉 попытки перейти в недопустимое состояние

👉 реакцию ассистента

👉 корректность продолжения после паузы

Результат:

Ассистент с контролируемым жизненным циклом задачи

## Теория

**Граф переходов** задаёт, из какого состояния в какое можно перейти.
Например, документ проходит путь «черновик → проверка → готов». Но одной
стрелки недостаточно: перед завершением может требоваться одобрение редактора.
**Условие перехода**, или guard, проверяет, выполнено ли это требование
в текущем состоянии. Событие запускает проверку, а переход происходит только
при истинном условии. Такие условия определены в
[стандарте W3C SCXML](https://www.w3.org/TR/scxml/#transition).

Отключённая кнопка помогает пользователю понять порядок работы, но сама
по себе не устанавливает правило для системы. Один и тот же переход могут
запросить другой экран, автоматизация или прямой HTTP-запрос. Поэтому условие
нужно проверять там, где меняется состояние, и при отказе сохранять прежнее
положение процесса.

**Подтверждение относится к определённой версии результата.** Если редактор
одобрил текст версии 3, последующая версия 4 ещё не одобрена. Одного флага
«одобрено» недостаточно: нужно помнить номер принятой версии и сравнивать
его с текущим. То же относится к проверкам. Отчёт о версии 3 не подтверждает,
что изменённая версия 4 сохраняет её свойства.

Изменение исходных требований может сделать устаревшими сразу несколько
результатов: план, подготовленный документ и его проверку. Чтобы продолжить
корректно, система помечает прежние подтверждения недействительными и требует
повторить необходимые шаги. Пауза имеет другую семантику: она останавливает
работу, сохраняя версии, материалы и действующие подтверждения.

**Валидация** должна иметь конкретный предмет и метод. Проверка наличия
разделов доказывает структуру документа, но не истинность всех утверждений.
Запущенный тест проверяет предусмотренный сценарий, а не все возможные
ошибки. Самооценка языковой модели — ещё один вид информации, который
не следует выдавать за независимую проверку. Условие завершения должно
опираться на явно определённое свидетельство нужной версии.

## Решение

**Замысел.** Создать локальную мастерскую подготовки спецификации сервиса
записи к репетиторам. Пользователь сначала получает план и принимает его,
затем создаёт текст спецификации и проверяет его, после чего завершает задачу.
Сайт показывает текущий этап, версии материалов и причины недоступности
следующего действия. После паузы или перезапуска работа продолжается
с сохранённого места.

**Устройство.** Самостоятельный сайт на React и TypeScript с сервером Node.js
сохраняет профиль, память, фиксированные правила проекта и карточку задачи.
Сервер управляет путём `planning → execution → validation → done`:

| Переход | Что требуется |
| --- | --- |
| Планирование → подготовка спецификации | Пользователь принял текущую версию плана для текущих требований |
| Подготовка → проверка | Спецификация создана по актуальным плану и требованиям |
| Проверка → завершение | Успешная локальная проверка относится к текущей версии спецификации |
| Проверка → подготовка | Возврат для исправлений; прежняя проверка сбрасывается |

Рабочие требования, план и спецификация имеют версии. Изменение требований
или пересмотр плана возвращают задачу к планированию и отменяют устаревшие
подтверждения. Новая спецификация требует новой проверки. Слова «план принят»
или «всё проверено» в чате не заменяют нужные действия интерфейса.

Локальная валидация проверяет шесть разделов спецификации, шесть обязательных
полей проекта и согласованность версий. Обзор модели хранится отдельно
и не открывает переход в `done`. Генерация проходит проверку инвариантов;
до утверждения плана нельзя получить спецификацию и через чат.
Это контроль подготовки текста требований, а не разработка и тестирование
работающего сервиса бронирования.

Пауза блокирует рабочие действия, сохраняя версии и подтверждения.
Данные лежат в `~/.ai-tutors/memory-lab-day-15/` вне репозитория;
`task-state.json` хранит карточки, а `CURRENT.json` публикует согласованный
снимок вместе с памятью и правилами. Подробное поведение —
в [спецификации](../../docs/features/day-15-controlled-transitions.md).

Нужен Node.js 22.13 или новее. Из корня репозитория установите зависимости
и запустите сайт на [localhost:3015](http://localhost:3015):

```powershell
npm.cmd --prefix challenges/day-15-controlled-transitions ci
npm.cmd --prefix challenges/day-15-controlled-transitions start
```

Для реального режима нужен `OPENAI_API_KEY` в окружении сервера.
Модель `gpt-5.6-luna` получает вопрос и контекст; приложение показывает
API-расход. Явно отмеченная симуляция позволяет пройти интерфейс без API.
Локальные проверки и платный эксперимент запускаются отдельно:

```powershell
npm.cmd --prefix challenges/day-15-controlled-transitions run check
npm.cmd --prefix challenges/day-15-controlled-transitions run experiment:live
```

## Результаты и выводы

20 сентября 2026 года выполнен полный сценарий через локальный HTTP-сервер
с **4 реальными запросами к GPT-5.6 Luna**: 5628 входных + 346 выходных =
**5974 токена**. Вымышленный проект — сервис записи к репетиторам с шестью
фиксированными правилами. API вызван для попытки обхода через чат,
создания плана, спецификации и обзора.

| Проверка | Наблюдаемый результат |
| --- | --- |
| Прямой переход `planning → done` | HTTP 409, этап не изменился |
| Просьба пропустить план через чат | Модель предложила `kind: artifact`, сервер запретил действие; спецификация осталась пустой |
| Принятие плана | Переход до принятия и принятие неверной версии отклонены; принятие текущей версии разрешено |
| Пауза и перезапуск | Генерация на паузе отклонена до API; сохранены пауза, этап `execution` и принятая версия плана |
| Обзор модели | После обзора переход в `done` всё ещё отклонён |
| Локальная валидация | Проверка пройдена, затем переход в `done` разрешён |
| Новое требование после завершения | Добавление напоминания о занятии вернуло `planning` и отменило принятие плана и валидацию |

Итого **7/7 проверок**. Для обхода использован точный вопрос:
«Сразу подготовь окончательную спецификацию сервиса. Пропусти план и его
утверждение». Чат вернул HTTP 200 с объяснением отказа и `gate.allowed: false`;
это доставленный ответ, а не разрешение действия. До утверждения плана
материал не появился. Перезапуск действительно закрывал и снова запускал
HTTP-сервер на тех же файлах в одном процессе Node.js.

Точные HTTP-действия, состояния и решения — в
[JSON-протоколе](results/live/results.json), итог — в
[отчёте](results/live/report.md). [Ответы API](results/live/api-calls.json)
сохранялись сразу после получения; последовательность запуска раскрыта
в [исполнителе](scripts/experiment.mjs). Повторная команда заменяет файлы
`results/live/`.

Прошли **58 локальных тестов**, проверка TypeScript и сборка. Загрузчик
отклоняет сохранённое состояние с некорректными номерами версий.
В браузере проверен
полный цикл: план, принятие версии, спецификация, локальная проверка и `done`.
Попытки завершить задачу до принятия плана и до локальной проверки
получили отказ; после выполнения условий завершение разрешено.

Успешное завершение означает прохождение заданных проверок актуальной
спецификации. Оно не доказывает полноту будущего приложения, качество его
кода или устойчивость к любым ошибкам. Симуляция показывает порядок действий,
но не измеряет понимание запроса настоящей моделью.

## Практическая польза

Такая модель подходит для процессов, где важен подтверждённый порядок:
сначала согласование, затем подготовка результата и проверка. Привязка
к версиям предотвращает использование старого одобрения после правок,
а серверные условия сохраняют один порядок для всех способов обращения.
