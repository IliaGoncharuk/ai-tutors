# День 16 — подключение MCP

## Исходное задание

🔥 День 16. Подключение MCP

Установите MCP SDK / клиент (или поднимите MCP-сервер, если используете локальный вариант)

Сделайте минимальный код, который:

👉 устанавливает MCP-соединение
👉 получает от MCP список доступных инструментов

Проверьте:

👉 соединение устанавливается
👉 список инструментов корректно возвращается

Результат:

Код, который подключается к MCP и выводит список доступных инструментов

## Теория

**Model Context Protocol (MCP)** — протокол, через который приложение узнаёт
о возможностях внешней программы и вызывает их по согласованным правилам.
Приложение-хост управляет работой пользователя; MCP-клиент внутри него поддерживает
соединение; MCP-сервер предоставляет инструменты. Языковая модель для самого
соединения не требуется. Например, календарь может предоставлять инструмент
поиска встреч, а разные приложения использовать одно и то же описание его входа.
[Архитектура MCP](https://modelcontextprotocol.io/docs/learn/architecture).

**Инструмент** состоит из имени, назначения и схемы параметров. JSON Schema
описывает допустимые типы и значения: например, поле `month` должно быть целым
числом от 1 до 12. Получение списка инструментов не означает их выполнение.
Сначала клиент узнаёт доступные действия через `tools/list`, затем при необходимости
выполняет выбранное через `tools/call`.

**Транспорт** доставляет сообщения между клиентом и сервером. Для локальной
программы удобен `stdio`: клиент запускает дочерний процесс и обменивается
сообщениями через его стандартный ввод и вывод. Поэтому обычные диагностические
логи сервера должны идти в `stderr`, иначе они могут нарушить поток протокола.
Для сетевого соединения существует Streamable HTTP.
[Транспорты SDK](https://ts.sdk.modelcontextprotocol.io/server).

```text
Хост → клиент → initialize → сервер
              ← возможности сервера
              → tools/list
              ← имена, описания, схемы
```

Инициализация согласует версию протокола и возможности сторон. Успешный запуск
процесса сам по себе ещё не доказывает готовность сервера: нужен ответ на
инициализацию и корректный ответ на запрос списка. После окончания работы
клиент закрывает соединение и завершает принадлежащий ему процесс.
[Клиент SDK](https://ts.sdk.modelcontextprotocol.io/client).

## Решение

**Замысел.** Создать локальную лабораторию, в которой человек нажимает
«Подключить сервер», видит его название, доступные действия и последовательность
обмена сообщениями. Дополнительная консольная команда решает исходное задание
минимальным способом: подключается, печатает список и отключается. Проверка
должна использовать настоящий отдельный процесс, а не заранее нарисованный список.

**Устройство.** React-интерфейс обращается к Node.js-серверу. Тот создаёт MCP-клиент
официального SDK и запускает `server/mcp-server.mjs`. Сервер регистрирует
`connection_info` с параметром `detail: short | full`. Его описание возвращается
через MCP. В этом дне инструмент описывает подключение; обращения к API Трекера
и языковой модели не нужны. Сайт позволяет обновить список, отключиться и
подключиться заново. Журнал показывает события клиента, а не полный сетевой дамп.

Нужен Node.js 22.13 или новее. Из корня репозитория установите зависимости
и запустите сайт на [localhost:3016](http://localhost:3016):

```powershell
npm.cmd --prefix challenges/day-16-mcp-connection ci
npm.cmd --prefix challenges/day-16-mcp-connection start
```

Вывести каталог инструментов без браузера и выполнить локальные проверки:

```powershell
npm.cmd --prefix challenges/day-16-mcp-connection run tools
npm.cmd --prefix challenges/day-16-mcp-connection run check
```

## Результаты и выводы

Проверки находятся в [tests/connection.test.mjs](tests/connection.test.mjs).
Они запускают MCP-процесс, проверяют имя сервера, схему параметров, допустимый
и недопустимый вызов, повторное соединение и завершение дочернего процесса.
Отдельно проверяются недоступный сервер и ограничение запросов локальным сайтом.
Фактические результаты выполнения фиксируются в [протоколе](results/verification.md).

Наличие инструмента в каталоге подтверждает его регистрацию, но не доступ
к внешнему сервису. Этот день проверяет протокол; интеграция с настоящим
Трекером относится к следующему самостоятельному заданию.

## Практическая польза

Такой экран помогает диагностировать подключение MCP до добавления модели:
отдельно проверить запуск процесса, согласование протокола и обнаружение
инструментов. Тот же принцип применим к календарю, базе знаний или файловому сервису.
