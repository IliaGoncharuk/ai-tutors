# День 11 — модель памяти агента

## Исходное задание

День 11. Модель памяти агента

Опишите и реализуйте модель памяти для агента

Разделите информацию минимум на 3 типа:

👉 краткосрочная (текущий диалог)

👉 рабочая (данные текущей задачи)

👉 долговременная (профиль, решения, знания)

Сделайте так, чтобы:

👉 разные типы памяти хранились отдельно

👉 вы явно выбирали, что и куда сохраняется

Проверьте:

👉 какие данные попадают в каждый слой

👉 как это влияет на ответы агента

Результат:

Агент с явной моделью памяти (memory layers)

## Теория

**Память агента** — сведения, которые программа сохраняет и использует
в последующих обращениях к языковой модели. **Контекст** — то, что модель
получает для конкретного ответа. Это разные вещи: факт может лежать
в хранилище, но не попасть в запрос. Для продолжения диалога приложение
передаёт нужные предыдущие сообщения или использует механизм сохранения
состояния API. Самостоятельная сборка истории описана в
[документации OpenAI](https://developers.openai.com/api/docs/guides/conversation-state).

Память удобно разделять по назначению и сроку использования:

| Слой | Что сохраняет | Пример |
| --- | --- | --- |
| Краткосрочный | Недавние сообщения и уточнения текущего разговора | «Сравни второй вариант с первым» |
| Рабочий | Цель, условия и промежуточные результаты одной задачи | «Для этой поездки бюджет — 20 000 рублей» |
| Долговременный | Устойчивые предпочтения, принятые решения и накопленные знания | «В поездках предпочитаю поезда» |

У этих сведений разный жизненный цикл. Смена темы разговора может сделать
недавние реплики бесполезными, но бюджет остаётся нужен до завершения поездки,
а предпочтение транспорта — и при планировании следующей. Поэтому полезно
задавать отдельно правила записи, чтения, обновления и удаления. Названия
слоёв служат способом организации системы; важнее точно определить их границы.

**Запись** решает, какой факт и на какой срок сохранить. **Извлечение** выбирает,
что показать модели сейчас. Если сохранять каждую реплику как постоянный факт,
случайное предложение может стать ложным предпочтением. Если передавать всю
историю без отбора, растут объём контекста и количество устаревших сведений.
У каждой долговечной записи полезно знать источник, а для противоречий —
заранее определить приоритет актуальных данных.

Разделение файлов само по себе не доказывает пользу памяти. Проверка должна
проследить цепочку «факт сохранён → включён в запрос → использован в ответе».
Чтобы выяснить влияние одного слоя, задают одинаковый вопрос с ним и без него
из одинакового исходного состояния. Ответы одной проверки не должны становиться
памятью следующей. При этом даже правильный формат ответа не гарантирует
правильных фактов:
[документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)
отдельно отмечает возможность содержательных ошибок.

## Решение

**Замысел.** Создать локальную лабораторию, где человек общается с агентом
и сразу видит, что тот помнит. Рядом с чатом находятся три слоя памяти:
пользователь сам сохраняет нужный факт в данные задачи или долговременные
сведения. Затем он может задать один вопрос с разным составом памяти
и сопоставить ответы. Такая демонстрация связывает каждое действие сохранения
с видимым изменением контекста.

**Устройство.** Это самостоятельный сайт на React и TypeScript с локальным
сервером Node.js. Сервер хранит последние шесть сообщений в `sessions.json`,
рабочие сведения — в `tasks.json`, долговременные — в `long-term.json`.
Данные лежат в `~/.ai-tutors/memory-lab-day-11/` вне репозитория.
Указатель `CURRENT.json` публикует согласованную версию всех файлов.

Обычная переписка пополняет только краткосрочную память. Рабочие и
долговременные записи меняются вручную. Новый диалог сохраняет остальные
слои, новая задача получает пустые диалог и рабочую память. Продолжение
восстанавливает сохранённое состояние. Сайт показывает фактический контекст
API и сравнивает четыре варианта из одного снимка: все слои, без краткосрочного,
без рабочего и без долговременного. Ответы сравнения в диалог не записываются.
Подробные правила — в [спецификации](../../docs/features/day-11-memory-layers.md).

Нужен Node.js 22.13 или новее. Команды выполняются из корня репозитория.
Первая устанавливает зависимости,
вторая запускает API и сайт на [localhost:3011](http://localhost:3011):

```powershell
npm.cmd --prefix challenges/day-11-memory-layers ci
npm.cmd --prefix challenges/day-11-memory-layers start
```

По умолчанию ответы получает `gpt-5.6-luna` через OpenAI; ключ должен быть
в серверной переменной окружения `OPENAI_API_KEY`. Браузер его не получает.
Каждая отправка и каждый вариант сравнения расходуют API-токены; сайт показывает
фактический расход. Для знакомства без API можно вручную включить демонстрацию:
она явно помечена как симуляция и не оценивает качество модели.

Локальные тесты, проверка типов и сборка выполняются без платных запросов.
Вторая команда отдельно запускает реальный эксперимент на вымышленных данных
и сохраняет протокол:

```powershell
npm.cmd --prefix challenges/day-11-memory-layers run check
npm.cmd --prefix challenges/day-11-memory-layers run experiment:live
```

## Результаты и выводы

20 сентября 2026 года выполнены **6 реальных запросов к GPT-5.6 Luna**:
2779 входных + 268 выходных = **3047 токенов**. Сценарий — вымышленное техническое
задание сервиса записи к репетиторам. В рабочую память явно добавлены название
проекта, длительность занятия «45» и формат «веб-приложение»; в долговременную —
язык «русский» и часовой пояс `Asia/Yekaterinburg`. В короткий диалог вручную
помещены просьба сделать акцент на отмене занятия и учебное подтверждение
ассистента. Эти две исходные реплики — подготовленные данные, не ответы API.

Один вопрос просит вернуть шесть полей JSON: `project`, `minutes`, `delivery`,
`language`, `timezone`, `focus`; неизвестные значения должны быть `null`.
Четыре варианта состава памяти, новый диалог и новая задача используют
независимые копии исходного состояния. Точные записи, вопрос, инструкции,
переданные сообщения и ответы — в [полном протоколе](results/live/results.json);
таблица и расход — в [отчёте](results/live/report.md), методика —
в [исполнителе эксперимента](scripts/experiment.mjs).

| Проверка | Строго совпавшие поля, включая null |
| --- | ---: |
| Все слои | 6/6 |
| Без краткосрочной памяти | 6/6 |
| Без рабочей памяти | 6/6 |
| Без долговременной памяти | 6/6 |
| Новый диалог | 6/6 |

Итого **35/36**. Отключение каждого слоя убрало соответствующие факты из
ответа: временный акцент, параметры проекта или сведения пользователя.
Новый диалог сохранил рабочие и долговременные данные, новая задача — только
долговременные. В последней проверке модель, однако, вернула в `focus`
«подготовка проекта приложения записи к репетиторам» вместо `null`.
Эта формулировка повторяет общую роль из инструкции, хотя вопрос отдельно
определяет `focus` как временный акцент диалога. В фактическом запросе диалог
отсутствовал, а рабочая память была пустой: это ошибка интерпретации доступного
контекста, а не свидетельство переноса старой рабочей памяти.

Оценщик сравнивает значения и типы буквально. Он может не засчитать правильное
перефразирование, но здесь расхождение содержательное: вместо неизвестного
значения подставлена другая характеристика. Исходный ответ и оценка сохранены.
Один короткий запуск не измеряет устойчивость модели и качество свободного
обсуждения проекта. Повторная команда эксперимента заменяет файлы `results/live/`.

Прошли 20 локальных тестов, включая HTTP-проверки, проверка TypeScript
и сборка. `npm audit` сообщил 0 известных уязвимостей. В браузере проверены
загрузка примера, диалог в режиме симуляции, четыре варианта сравнения,
ручное сохранение, новый диалог и восстановление после перезагрузки страницы.
Реальные ответы модели проверены отдельным экспериментом выше.

## Практическая польза

Такая модель подходит помощнику, который ведёт несколько задач и сохраняет
общие предпочтения пользователя. Видимые слои помогают понять причину ошибки:
факт не сохранили, не передали модели или модель неверно его использовала.
Явный выбор места записи позволяет сохранять полезные сведения, не превращая
каждую случайную реплику в постоянное правило.
