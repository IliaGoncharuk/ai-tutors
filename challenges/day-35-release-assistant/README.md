## Теория

**Релиз** — зафиксированная версия продукта, которую можно передать
пользователям. Подготовка релиза и его публикация — разные этапы. Сначала
определяют состав изменений, проверяют работоспособность и описывают
последствия; затем человек принимает решение о версии и распространении.
Наличие новых коммитов само по себе не означает готовности продукта.

**Диапазон изменений** задаётся исходным и конечным коммитами. Сравнение
с последним тегом показывает отличие от ранее отмеченной версии; сравнение
с предыдущим коммитом подходит для маленького шага разработки. Незакоммиченные
файлы не принадлежат фиксированной версии. Если включить их в отчёт, он станет
черновиком будущего состояния и должен явно это показывать.
[Git: сравнение состояний](https://git-scm.com/docs/git-diff).

**Проверки готовности** зависят от проекта. Для библиотеки это могут быть
модульные тесты и сборка, для учебного сайта — запуск, проверка ссылок и
инструкция демонстрации. Успешная команда доказывает только прохождение этой
команды с конкретными входами. Отсутствие настроенных проверок и пропущенная
проверка не равны успеху; код возврата с ошибкой не может быть исправлен
положительной оценкой языковой модели.

**Release notes** объясняют изменения пользователю: что добавилось, что
исправлено и на что обратить внимание. Перечень файлов полезен как основание,
но не заменяет описание поведения. AI может преобразовать технические diff
в понятный черновик, однако способен приписать изменению несуществующий эффект.
Поэтому утверждения связывают с файлами, а факты запуска проверок передают
отдельно и не позволяют модели менять их статус.

**Версия продукта** при семантическом версионировании имеет вид MAJOR.MINOR.PATCH.
Несовместимое изменение публичного API повышает основную версию, совместимое
добавление возможностей — дополнительную, совместимое исправление — номер
исправления. Применять правило можно только при определённом публичном API.
Автоматическое чтение diff не всегда позволяет установить совместимость,
поэтому решение о номере версии требует проверки договора с пользователями.
[Спецификация SemVer](https://semver.org/lang/ru/).

**Переносимая автоматизация** отделяет механизм от настроек конкретного проекта.
Git сообщает факты, конфигурация определяет команды, а приложение собирает
единый отчёт. Аргументы команд следует передавать массивом без сборки shell-
строки: это сохраняет границы аргументов и уменьшает риск интерпретации
спецсимволов. При этом сами команды проекта должны быть доверенными: запуск
тестов является исполнением кода, а не изолированной проверкой текста.
[Node.js: execFile](https://nodejs.org/api/child_process.html#child_processexecfilefile-args-options-callback).

```text
Диапазон Git + правила проекта → факты и результаты проверок
                                      ↓
                              AI-черновик описания
                                      ↓
                     локальный отчёт → решение человека
```

## Решение

Замысел — автоматизировать повторяющуюся подготовку pet-проекта к выпуску:
собрать изменения, выполнить выбранные проверки и получить понятный черновик
описания. Пользователь добавляет CLI (инструмент командной строки) к своему
проекту, задаёт конфигурацию один раз и повторяет одну команду перед релизами.
Проверка решения должна включать настоящий AI Tutors и независимый Git-проект,
а также намеренно неуспешную проверку, которую AI не сможет объявить успешной.

По уточнению пользователя инструмент не привязан к AI Tutors и не генерирует
новые учебные проекты. Пакет называется `ai-pet-release`, команда — `ai-release`.
Нужны Node.js 22.13+ и Git. Внешних npm-зависимостей нет. Другие стеки
поддерживаются командами конфигурации: например, Python, Gradle или Go должны
быть установлены отдельно. Инструмент не устанавливает зависимости проекта.

### Запуск из исходников

Из папки задания сначала посмотрите справку:

```powershell
node cli.mjs --help
node cli.mjs inspect --repo ../..
```

`inspect` только читает репозиторий и показывает диапазон, список изменений
и наличие обязательных файлов. Без `--base` выбирается ближайший тег; если
его нет — предыдущий коммит. Для первого коммита используется начальное
пустое состояние. Явный `--base` предпочтителен для повторяемого отчёта.

Подготовить отчёт AI Tutors вместе с текущими незакоммиченными изменениями:

```powershell
node cli.mjs prepare --repo ../.. --include-working-tree --run-checks --out ../../.local-days-31-35/release-drafts
```

`--run-checks` разрешает выполнить доверенные команды проекта. Без этого
флага они получают статус `skipped`. Для отчёта без облака добавьте `--no-ai`:
ключ и журнал API тогда не нужны. Для AI нужен `OPENAI_API_KEY` в окружении.

### Подключение к другому pet-проекту

В папке своего проекта установите инструмент из локальной папки исходников:

```powershell
npm.cmd install --save-dev "C:/projects/ai-tutors/challenges/day-35-release-assistant"
npx.cmd --no-install ai-release init --repo .
```

Первый путь замените путём к своей копии задания. `init` создаёт
`ai-release.config.json` и отказывается перезаписывать существующий файл.
При наличии npm-скрипта `check` он выбирается автоматически; иначе используются
имеющиеся `test` и `build`. Для другого стека укажите свои команды:

```json
{
  "name": "my-pet-project",
  "contextPaths": ["README.md", "docs/", "src/"],
  "requiredFiles": ["README.md"],
  "checks": [
    { "name": "tests", "command": ["python", "-m", "unittest"], "cwd": ".", "timeoutMs": 60000 }
  ]
}
```

Затем перед релизом:

```powershell
npx.cmd --no-install ai-release prepare --repo . --base v0.1.0 --run-checks --out ./release-drafts
```

Замените `v0.1.0` реальным тегом или коммитом. Добавьте `release-drafts/`
в `.gitignore` своего проекта. Можно установить и собранный `.tgz` через
`npm install --save-dev путь/ai-pet-release-1.0.0.tgz`:
[готовый локальный пакет](artifacts/ai-pet-release-1.0.0.tgz). Публикация в npm не нужна.

Конфигурация и CLI не требуют переписывания исходников инструмента.
Команды исполняются без shell, с ограниченным окружением без `OPENAI_API_KEY`;
системные инструменты должны быть доступны через PATH. Команда `node`
использует текущий Node.js; `npm` отдельно поддержан в Windows. Batch-скрипты
других инструментов запускайте через соответствующий установленный runtime.

Каждый запуск создаёт новую папку с `report.json` и `release-notes.md`.
Статус рассчитывается кодом: `blocked` при провале проверок или отсутствии
обязательных файлов, `needs-review` при пропусках, грязном дереве или
сокращении контекста, `ready-for-human-review` при полном прохождении выбранных
проверок. Последний статус всё равно требует решения человека.
CLI возвращает код 2 для заблокированного отчёта, 1 для ошибки инструмента,
0 для созданного незаблокированного черновика.

### Локальный сайт

`npm.cmd start` из папки задания открывает
[127.0.0.1:3035](http://127.0.0.1:3035). Страница демонстрирует тот же механизм
на AI Tutors, позволяет включить проверки и открыть сохранённые отчёты.
Для других репозиториев используется CLI. Остановка сервера — Ctrl+C.
`npm.cmd run check` выполняет локальные тесты; `npm.cmd run experiment`
повторяет реальную серию с облачной генерацией.

В OpenAI передаются выбранные тексты и diff, имена файлов, заголовки коммитов
и статусы проверок. Скрытые, секретные и служебные файлы исключаются; типичные
значения секретов маскируются. Это не универсальный сканер утечек: используйте
инструмент только с корпусом, который разрешено передавать провайдеру.
Лимиты контекста и исключения явно записываются в отчёт. Общий бюджет новых
вызовов — по [ADR серии](../../docs/decisions/0019-days-31-35-project-assistants.md).

## Результаты и выводы

Локально прошли 6 тестов: два настоящих коммита временного проекта, исключение
секретов, отказ перезаписи конфигурации, блокировка при провале команды,
отчёт без AI, общий бюджет, расчёт статуса и HTTP-граница. Модель в тесте
провала подменена, поэтому этот тест не является облачным экспериментом.
Контрольный прогон от 2026-10-18 —
[`results/experiment.json`](results/experiment.json): первый отчёт относится
к настоящему рабочему дереву AI Tutors, второй — к независимому `pet-calendar`.
CLI установлен во второй проект из локального `.tgz`, затем запущен из
установленного пакета с настоящим облачным вызовом. Тест `pet-calendar`
проверил форматирование дней `5 → 05`, `12 → 12` и завершился кодом 0.

Все пять настроенных проверок AI Tutors прошли. Статус отчёта — `needs-review`,
поскольку дерево содержит незакоммиченные изменения и контекст сокращён.
Во втором проекте проверка прошла, но исключённый lock-файл также оставил
статус `needs-review`. Результаты не выданы за опубликованный релиз.
Черновики — [AI Tutors](results/ai-tutors-release-notes.md) и
[pet-calendar](results/pet-calendar-release-notes.md).

Модель правильно описала изменение формата дней, однако добавила избыточные
оговорки. В отчёте AI Tutors она пишет, что наличие AGENTS.md нельзя подтвердить,
хотя отдельная программная проверка подтвердила файл. Такая оговорка не меняет
факты `required` и показывает, почему черновик необходимо читать человеку.
Облако использовалось дважды, расчётно $0,00744315. Итог всей серии: 73 попытки
API-вызовов, оценка $0,02900011 плюс сохранённый резерв $0,00427825 от одного
отклонённого запроса дня 34. Это существенно ниже общего лимита $1.

Инструмент не меняет номер версии, не создаёт коммиты/теги, не делает push
и не публикует релиз. Он не доказывает отсутствие ошибок и не проверяет весь
проект автоматически: состав проверок задаёт владелец. Большие релизы могут
требовать разбиения или ручного анализа файлов вне сокращённого контекста.

## Практическая польза

Одна команда заменяет ручное собирание diff, результатов тестов и черновика
описания перед выпуском небольшого проекта. Отчёт сохраняет доказательства
проверок, явно показывает пропуски и помогает человеку принять решение о
готовности версии без автоматической публикации.
