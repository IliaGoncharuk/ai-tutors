# День 8 — работа с токенами

Отдельный CLI-агент показывает размер нового сообщения, всей истории до хода,
полного входа с инструкциями и ответа модели. Таблица и текстовый график помогают
сравнить короткий и длинный диалоги. Сценарий переполнения показывает, где
останавливается запрос и что остаётся в памяти агента.

## Запуск

Нужен Node.js 22.13+. Команды выполняются из каталога задания:

```powershell
cd challenges/day-08-token-accounting
npm ci
npm run demo
```

`demo` запускает **симуляцию без API, ключа и списаний**: 3 хода, 20 ходов,
затем переполнение учебного окна 8192. Симулятор использует условный разбор слов,
чисел и пунктуации с добавкой за оформление сообщений. Это не токенизатор Luna
и не оценка её реальных токенов. Ответы заданы локальной логикой. Отмеченные
суммы USD только иллюстрируют расчёт по тарифам; они не являются расходом счёта.

Для обычного диалога с OpenAI API:

```powershell
npm start
```

Ключ читается из `OPENAI_API_KEY` в окружении; `.env` автоматически не загружается.
Перед каждым ответом выполняются 2–3 обращения к endpoint подсчёта, затем одна
генерация. Они отправляют соответствующие части диалога OpenAI. Подсчёт нового
сообщения и истории нужен для учебного сравнения; для обычной проверки окна
достаточно подсчёта полного входа. Повторных попыток SDK нет, timeout — 60 секунд.

История хранится в `<домашний каталог>/.ai-tutors/day-08/messages.json`, отдельно
от Дня 7. При необходимости задайте `TOKEN_AGENT_HISTORY_FILE` — абсолютный путь
**вне публичного репозитория**. Один файл предназначен для одного процесса.
Сохраняются только пары сообщений, без ключей и статистики. Формат и механизм
атомарной замены повторно используются из
[Дня 7](../day-07-context-persistence/README.md).

| Команда | Поведение |
| --- | --- |
| Текст | Подсчитать вход, проверить окно, получить ответ и сохранить полный ход |
| `/history` | Показать сохранённые сообщения |
| `/stats` | Показать таблицу, график и сумму за текущий запуск без API-вызова |
| `/reset` | Очистить историю в памяти и на диске; сохранить расход текущего запуска |
| `/exit` | Завершить CLI |

## Как читать метрики

| Метрика | Точный смысл |
| --- | --- |
| Новое сообщение | Серверный подсчёт отдельного сообщения `user`, включая его оформление |
| История до хода | Серверный подсчёт всех прежних `user`/`assistant`, без нового сообщения и инструкций; пустая история — 0 |
| Полный вход | Подсчёт инструкций, всей истории и нового сообщения в одном запросе |
| Usage вход | Фактический `usage.input_tokens` полученного ответа |
| Ответ | `usage.output_tokens`, включая reasoning; reasoning отдельно показан как часть ответа |
| Кеш | Прочитанные и записанные токены из `input_tokens_details` |
| Контекст | Полный вход / лимит окна; отдельно показан резерв ответа и остаток с резервом |
| USD ход / сумма | Оценка стоимости генерации по usage и сумма известных оценок за текущий запуск |

Первые три числа получены **для разных запросов**. У каждого своё служебное
оформление, поэтому «новое + история» не обязано равняться «полный вход».
Реализация использует `responses.inputTokens.count`, а не деление числа символов
на четыре. Полный подсчёт и генерация получают одинаковые `model`,
`instructions`, `input` и `reasoning`; отличие между подсчётом и usage выводится
как `Δ`. Расход всегда берётся из usage, когда он доступен.
[Официальная документация подсчёта](https://developers.openai.com/api/docs/guides/token-counting).

`?` означает отсутствие достоверных данных. Например, отклонённый API-запрос
может не содержать usage. Он не превращается в «0 токенов» или «$0»: итог
показывает известную сумму и число вызовов с неизвестными метриками.
При локальном отказе генерация не отправляется и её расход равен нулю.
Стоимость обращений к endpoint подсчёта в калькулятор не включена: его биллинг
не подтверждён использованной документацией. Итог не является полной выпиской
счёта, не включает налоги и индивидуальные условия аккаунта.

История переживает перезапуск, статистика — только текущий процесс. Поэтому
стоимость прошлых запусков не восстанавливается из текстов сообщений. `/stats`
показывает историю измерений; точный размер восстановленного контекста будет
вычислен перед следующим обычным сообщением.

## Теория

### Токены и контекст

Токен — единица представления текста моделью: слово может занимать один или
несколько токенов, а пробелы, знаки и язык влияют на разбиение. Символ, слово и
токен не взаимозаменяемы. Кроме текста, запрос содержит обозначения ролей и
границ сообщений. Счётчик полного входа учитывает эти накладные расходы.

Окно контекста ограничивает объём информации, который может участвовать в одном
обращении. Агент дня 8 использует консервативную проверку:

```text
полный вход + max_output_tokens <= contextLimit
```

Это локальное правило резервирования места для всего разрешённого ответа.
Если вход ещё помещается, но резерв уже нет, это отказ локальной защиты,
а не наблюдение ошибки модели. Значение `max_output_tokens` — верхняя граница;
оплата фактического ответа не равна этому резерву.

### Почему диалог дорожает

Как и в Дне 7, на каждом ходе отправляется вся переписка. Ответ прошлого хода
становится частью входа следующего. Если инструкции занимают `S` токенов,
каждый пользовательский запрос — `U`, ответ — `A`, то без служебных различий:

```text
вход на ходе k ≈ S + k·U + (k−1)·A
сумма входов за n ходов ≈ n·S + U·n(n+1)/2 + A·n(n−1)/2
```

При примерно одинаковой длине ходов текущий вход растёт линейно, а суммарный
расход входных токенов — квадратично. Размер истории учитывает каждый текст
один раз; сумма usage учитывает его повторную передачу. Это разные величины.

Кеширование может снизить цену повторно используемого префикса, но не делает
его короче и не расширяет окно. Сумма расходов растёт, однако цена отдельного
хода не обязана расти строго: меняются кеш и длина ответа. Локальная симуляция
не моделирует кеш и качество рассуждений модели. Восстановление слова «Кедр»
в симуляции подтверждает передачу истории, а не способность реальной модели
удерживать факты на большой дистанции.

### Расчёт стоимости

Калькулятор настроен на стандартные текстовые запросы `gpt-5.6-luna` с
`service_tier: default`, `reasoning.effort: none`. Проверенные 2026-09-13 тарифы
в USD за миллион токенов: обычный вход 0,20; кеш-чтение 0,02; кеш-запись 0,25;
выход 1,20. При входе **строго больше 272 000** тарифы всего запроса повышаются:
входные ×2, выходной ×1,5. Окно — 1 050 000, максимальный выход — 128 000.
Числовой профиль находится в [accounting.mjs](accounting.mjs).
[Карточка модели](https://developers.openai.com/api/docs/models/gpt-5.6-luna).

```text
обычный вход = input_tokens − cached_tokens − cache_write_tokens
цена = (обычный вход·Pinput + cached_tokens·Pcache
        + cache_write_tokens·Pwrite + output_tokens·Poutput) / 1 000 000
```

Для длинного входа сначала применяются указанные множители к тарифам.
`cached_tokens` и `cache_write_tokens` входят в `input_tokens` и не добавляются
к нему повторно. Аналогично reasoning уже входит в output. Если разбивка кеша
отсутствует или противоречива, токены могут быть известны, а цена останется `?`.
Неизвестная модель ответа или другой service tier также отключают расчёт цены.
[Документация кеширования и формула](https://developers.openai.com/api/docs/guides/prompt-caching).

### Что ломается при переполнении

При `truncation: disabled` слишком большой вход приводит к отказу API, обычно
HTTP 400 с `context_length_exceeded`. Нового ответа нет. День 8 сохраняет
последнюю успешную историю и отдельно показывает этап ошибки: подсчёт либо
генерация. Другой HTTP 400 не считается автоматически переполнением. HTTP 429
может означать квоту или лимит токенов в минуту (TPM), что отличается от размера
контекста одного запроса.

`status: incomplete` с причиной `max_output_tokens` — другая ситуация: генерация
началась, но не завершилась в лимите ответа. Её usage учитывается; незавершённая
пара не записывается в историю. Так же учитывается расход успешной генерации,
после которой не удалось записать JSON.
[Справочник Responses API](https://developers.openai.com/api/reference/typescript/resources/responses/methods/create).

Автоматического удаления ранних сообщений и compaction нет. Удаление старых
ходов освободило бы место, но могло бы убрать контрольное слово; сокращение
истории потребовало бы отдельного правила сохранения важных фактов. После
переполнения можно начать новый диалог через `/reset`. Если превышение вызвано
самим новым сообщением, нужно сократить и его. Лимит нового текста унаследован
от входной политики Дня 6: 8000 символов; он не является лимитом токенов модели.

## Сравнение и воспроизведение

Результат выполненного 2026-09-13 `npm run demo` — **условные токены симулятора**:

| Сценарий | Ходов генерации | Полный вход: первый → последний | Сумма input / output | Иллюстрация USD |
| --- | --- | --- | --- | --- |
| Короткий | 3 | 40 → 349 | 714 / 11 | 0,00015600 |
| Длинный | 20 | 40 → 5194 | 54 689 / 96 | 0,01105300 |
| Переполнение | 1 попытка после локального отказа | 13 474 > 8192 | Usage отсутствует | Неизвестно по usage; реальных списаний нет |

В обеих обычных сериях первое сообщение задаёт контрольное слово, последнее
просит его вернуть. Промежуточные сообщения содержат одинаковый учебный текст
и требуют короткого подтверждения. В длинной серии больше таких сообщений.
Последний пользовательский вопрос короткий: нагрузку создаёт именно история.
При переполнении синтетическая история остаётся без изменений.

Для измерений на реальной модели подготовлены две отдельные команды:

```powershell
# 3 + 20 генераций; перед ними 67 обращений к подсчёту при успешном прохождении.
npm run demo:live

# Измерить большой синтетический вход, проверить защиту и запросить отказ API.
npm run demo:overflow
```

Запускайте их после решения о расходах. `demo:live` использует память процесса,
а не личную историю CLI. `demo:overflow` начинает с 800 синтетических пар и
измеряет весь вход; при необходимости увеличивает его максимум до 4000 пар
за 4 измерения. Затем выполняет обычную проверку и одну диагностическую попытку
с обходом локального ограничения. Серверное сокращение остаётся отключённым.
Большой вход и ответы не сохраняются на диск; в отчёте остаются только метрики,
этапы и безопасные сообщения ошибок.

На каждую серию задан расчётный бюджет генерации $1. Перед отправкой он
проверяется по максимальному выходу и самому дорогому варианту входа — записи
всего входа в кеш. Неизвестная предыдущая стоимость останавливает серию.
Это программная оценка по указанным тарифам, а не ограничение биллинга аккаунта;
endpoint подсчёта в неё не входит. У интерактивного `npm start` такого бюджета
нет. Объём большого HTTP-запроса и ограничения аккаунта могут вызвать другой
отказ раньше контекстного; тогда сценарий завершается с ненулевым кодом и
**не утверждает**, что ошибка переполнения генерации воспроизведена.

## Проверки и устройство кода

```powershell
npm test
npm run lint
npm run demo
```

2026-09-13 прошли 16 тестов, проверка синтаксиса всех `.mjs` и три локальных
сценария. Тесты проверяют реальные HTTP-форматы установленного OpenAI SDK через
подменённый `fetch`, расчёт кеша и границу длинного тарифа, резерв контекста,
разницу 400/429, потерю usage, обрыв ответа, ошибку записи, сохранение UTF-8 и
восстановление истории между сеансами CLI, расход после сброса. Отдельно
проверен отказ запуска без ключа. Установка зависимостей выполнена из
локального npm-кеша. Реальные обращения к API Дня 8 не выполнялись; реальные
токены, стоимость, качество длинного диалога и отказ провайдера ещё не измерены.
