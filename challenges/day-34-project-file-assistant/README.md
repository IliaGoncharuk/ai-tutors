# День 34. Ассистент для работы с файлами проекта

## Исходное задание

День 34. Ассистент для работы с файлами проекта

Сделайте ассистента, который активно работает с файлами, а не просто отвечает текстом.

Через MCP или доступный вам tooling ассистент должен уметь:

👉 читать файлы проекта
👉 искать информацию по нескольким файлам
👉 анализировать содержимое
👉 создавать или изменять файлы

Примеры сценариев (реализуйте минимум 2):

👉 найти все места, где используется определённый компонент / API
👉 обновить документацию на основе изменений в коде
👉 сгенерировать новый файл (README / ADR / changelog)
👉 проверить соответствие файлов правилам или инвариантам
👉 подготовить diff или список изменений

Важно:

👉 ассистент сам инициирует работу с файлами
👉 вы задаёте задачу на уровне цели, а не “открой файл X”

Минимальный результат:

👉 ассистент работает минимум с 2–3 файлами
👉 изменения сохраняются или выводятся как diff
👉 результат можно воспроизвести повторно

Результат:

AI-ассистент, который выполняет реальные операции с файлами проекта

## Теория

**Агент с инструментами** отличается от обычного текстового помощника циклом
обратной связи. Модель выбирает операцию и аргументы, программа исполняет
разрешённое действие и возвращает наблюдение, после чего модель выбирает
следующий шаг. Ответ «я обновил документ» без успешного результата инструмента
не подтверждает изменение файла.

**Задача на уровне цели** описывает желаемый результат: «документация должна
соответствовать API». Она не задаёт последовательность открываемых файлов.
Чтобы достичь цели, агент сначала узнаёт структуру проекта, находит связанные
понятия, читает исходники и только затем выбирает изменение. Например,
перенос маршрута с `/api/v1/items` на `/api/v2/items` затрагивает не только
клиент, но и примеры запросов, документацию и вызывающий экран.

**Function calling** передаёт выбор операции через структурированные поля,
вместо попытки извлекать команду из свободного текста. Описание инструмента
объясняет его назначение, схема задаёт допустимые аргументы, а серверная
проверка определяет, разрешено ли действие на самом деле. Строгая схема
не заменяет проверку путей или бизнес-условий.
[OpenAI: function calling](https://developers.openai.com/api/docs/guides/function-calling).
MCP позволяет вынести эти операции в отдельный процесс с явным каталогом
возможностей и результатами вызовов.
[MCP: tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

```text
Цель → список файлов → поиск → чтение связанных исходников
                               ↓
       ответ ← проверка ← изменение выбранного документа
```

**Ограничение области записи** должно обеспечиваться программой. Запрет
в инструкции модели недостаточен: путь может содержать `..`, быть абсолютным
или вести через символическую ссылку за пределы каталога. Поэтому сравнивают
разрешённые относительные имена и фактическое расположение файлов. Для
учебной демонстрации отдельная рабочая копия позволяет повторять эксперимент,
не смешивая его с изменениями настоящего проекта.

**Diff** показывает, что было удалено и добавлено. Он полезен для проверки
изменения человеком и для воспроизводимого применения. Снимки «до» и «после»
дают дополнительное доказательство фактической записи. Если агент завершился
ошибкой после частичной записи, требуется либо откат изменённых им файлов,
либо честный отчёт о частично выполненной работе.

**Идемпотентность** означает, что повторное достижение уже выполненной цели
не создаёт новых побочных изменений. Например, второй запуск синхронизации
актуальной документации должен дать пустой diff. Простое совпадение имён
маршрутов ещё не доказывает правильность всех объяснений; автоматическая
проверка должна описывать, какие именно свойства она контролирует.

## Решение

Замысел — дать агенту небольшой понятный проект с намеренно устаревшей
документацией. Человек ставит одну из двух целей: найти использования API или
привести документацию в соответствие с кодом. Агент самостоятельно выбирает
файлы и инструменты, а сайт показывает чтения, результаты поиска, запись и
diff. Для проверки повторяемости обновление выполняется дважды.

`sample-project/` содержит четыре файла: README, клиент API v2, вызывающий
экран и описание API v1 с устаревшим маршрутом курсов. При запуске создаётся
рабочая копия в каталоге локальных данных серии; исходный пример в Git не
перезаписывается. Сценарий «Восстановить» возвращает только четыре известных
файла примера и не делает облачных вызовов.

MCP предоставляет `list_files`, `search_text`, `read_file`, `verify_workspace`.
В режиме обновления дополнительно доступен `write_file`, который может
изменять только `docs/api.md` рабочей копии. Код не редактируется. Модель сама
вызывает инструменты через Responses API; программа требует прочитать минимум
три разных файла до записи и проверяет результат. После ошибки разрешённый
документ восстанавливается из снимка начала запуска. Максимум — 13 шагов
генерации; произвольного shell-инструмента нет.

Из папки задания:

```powershell
npm.cmd ci
npm.cmd start
```

Команды устанавливают зависимости и открывают
[127.0.0.1:3034](http://127.0.0.1:3034). Выберите сценарий и задайте цель.
Для новых операций нужен `OPENAI_API_KEY` у серверного процесса; просмотр
сохранённых примеров бесплатен. Тексты прочитанных учебных файлов и цель
отправляются в OpenAI. Общий бюджет и рабочий каталог описаны в
[ADR серии](../../docs/decisions/0019-days-31-35-project-assistants.md).
Остановка — Ctrl+C.

`npm.cmd run check` проверяет границы записи, MCP, повторную запись и HTTP.
`npm.cmd run experiment` восстанавливает учебную копию и выполняет три
настоящих сценария: поиск, обновление, повторная проверка.

## Результаты и выводы

Исходный пример — [`sample-project`](sample-project/README.md). Точные цели,
все вызовы инструментов, прочитанные тексты, снимки до/после и ответы сохраняются
в [`results/experiment.json`](results/experiment.json); отдельный diff —
[`results/update.diff`](results/update.diff). Проверка от 2026-10-18:
прошли все 8 тестов, в том числе применение diff через `git apply --check`.

В поиске агент сам вызвал список, поиск, чтение четырёх файлов и проверку
расхождений: 7 операций, запись отсутствует. В обновлении прочитал три файла,
заменил v1 на v2 и courses на lessons, сохранил документ и прошёл проверку:
7 операций. Повторный запуск прочитал три файла, подтвердил соответствие
и оставил пустой diff: 6 операций. Это один воспроизводимый учебный сценарий,
а не доказательство надёжности агента для произвольного проекта.

Три успешных сценария потребовали 23 вызова модели. До них один запрос был
отклонён HTTP 400 из-за неполной схемы function calling; схема исправлена,
а резерв $0,00427825 оставлен в журнале как неизвестный расход. Расчётный
расход дня $0,00612475; общий итог дней 31–34 — $0,02155696 плюс этот резерв.

Проверка соответствия ищет маршруты из клиента в документе и отсутствие
старой версии; это узкий инвариант, не полноценная проверка документации.
Агент не умеет изменять произвольные файлы реального репозитория, создавать
коммиты или выполнять сгенерированный код. Эти границы позволяют воспроизвести
реальную запись без расширения полномочий.

## Практическая польза

Такой цикл помогает находить связанные использования API, объяснять
последствия изменений и поддерживать документацию рядом с кодом. Журнал
операций и diff позволяют отличить полезное выполненное изменение от
правдоподобного обещания помощника.
