# День 22 — первый RAG-запрос

## Исходное задание

🔥 День 22. Первый RAG-запрос

Реализуйте функцию:

👉 вопрос → поиск релевантных чанков → объединение с вопросом → запрос к LLM

Сравните:

👉 ответ модели без RAG
👉 ответ модели с RAG

Усиление:

👉 составьте мини-набор из 10 контрольных вопросов по вашей базе
👉 для каждого вопроса зафиксируйте:

- ожидание (что должно быть в ответе)
- какие источники должны быть использованы (если применимо)

Результат:

Агент с двумя режимами (с RAG / без RAG) + 10 контрольных вопросов и сравнение качества

## Теория

**RAG (Retrieval-Augmented Generation)** — генерация ответа с предварительным
поиском информации. Языковая модель продолжает текст на основе обучения и
текущего контекста; она не получает доступ к папке документов просто потому,
что папка существует рядом с программой. Приложение сначала ищет фрагменты,
затем явно помещает их в запрос. Это не дообучение: параметры модели не меняются.

```text
Документы → фрагменты → эмбеддинги → индекс
Вопрос → эмбеддинг → поиск → выбранные фрагменты + вопрос → модель → ответ
```

**Извлечение** и **генерация** решают разные задачи. Поиск должен доставить
достаточные доказательства, а модель — правильно их использовать. Например,
на вопрос о времени выдачи книг поиск может найти страницу библиотеки, но
выбрать раздел «История здания». Документ верный, а ответа в контексте нет.
Даже отличный генератор не восстановит неизвестное расписание надёжно.
[Поиск по эмбеддингам](https://developers.openai.com/api/docs/guides/embeddings).

**Top-K** — число лучших результатов, передаваемых дальше. Маленькое K
экономит контекст, но может пропустить нужный факт; большое добавляет шум,
повторы и расход токенов. Важны размер фрагмента, число источников и доступный
контекст. Оценка сходства говорит о близости текстов, а не о достоверности факта.

**Сравнение с базовым режимом** требует одинаковых вопросов, модели и общих
инструкций. Между режимами меняют наличие найденных документов. Иначе нельзя
понять, вызвано ли различие поиском, другой моделью или более подробным заданием.
Заранее записанный эталон должен перечислять проверяемые факты, а не требовать
буквального совпадения формулировки. Контрольные вопросы не индексируют вместе
с ответами: это дало бы системе готовую подсказку для теста.

**Метрики** следует разделять. Попадание нужного документа измеряет поиск.
Полнота и правильность фактов измеряют ответ. Наличие ключевых слов удобно
автоматизировать, но фраза «не знаю, какие профили есть» тоже содержит слово
«профили». Поэтому словарная проверка не заменяет смысловой разбор. Отказ
при отсутствии данных отличается от галлюцинации — неподтверждённого утверждения.

RAG уменьшает дефицит информации, но не гарантирует истинность: документы
могут устареть, поиск ошибиться, а модель сделать лишний вывод. Текст найденного
документа также не должен становиться инструкцией для приложения. Обычная
инструкция в запросе задаёт границу, но не является полной защитой от всех
возможных атак на модель.

## Решение

**Замысел.** Создать сайт с двумя ответами на один вопрос: модель отвечает
самостоятельно и с найденными документами. Пользователь выбирает контрольный
вопрос или вводит свой, запускает сравнение и раскрывает контекст каждого
ответа. Так можно увидеть не только итог, но и причину ошибки поиска.
Проверяем решение двадцатью реальными ответами на десять заранее заданных вопросов.

**Данные.** В [снимке](data/corpus.json) — 20 README учебного репозитория,
18 628 слов, около 37,3 условной страницы по 500 слов. Разделы `Исходное задание`
исключены. Набор вопросов, ожидаемые факты и документы находятся в
[questions.json](data/questions.json); эти эталоны не отправляются модели.
Готовые настоящие эмбеддинги поставляются в [индексе](data/index.json.gz).
Первый запуск импортирует их в локальную SQLite.

**Выполнение.** Функция `answer` в [rag.mjs](server/rag.mjs) получает вопрос,
режим и стратегию. В `plain` список документов пуст. В `rag` вопрос превращается
в эмбеддинг, локальный поиск выбирает пять фрагментов, а затем модель получает
JSON с вопросом и документами. Используется `gpt-5.6-luna`, `reasoning: none`,
лимит 1200 выходных токенов, `store: false`. Инструкции и модель одинаковы.
Сохраняются точный запрос, ответ, выбранные фрагменты, время и usage.
[Responses API](https://developers.openai.com/api/docs/guides/text),
[модель](https://developers.openai.com/api/docs/models/gpt-5.6-luna).

Интерфейс показывает новые ответы рядом. Вкладка результатов позволяет читать
сохранённый эксперимент без повторных вызовов. История текущего сравнения
сохраняется локально; если второй запрос не удался, первый остаётся в SQLite.

Нужен Node.js 22.13+ и `OPENAI_API_KEY` в окружении сервера для новых ответов.
Из папки задания:

```powershell
npm.cmd ci              # установить зависимости
npm.cmd start           # сервер http://127.0.0.1:3022
npm.cmd run check       # локальные тесты, типы, сборка
npm.cmd run experiment  # 10 вопросов × 2 реальных ответа
```

Остановка — Ctrl+C. Рабочие данные — `~/.ai-tutors/rag-campaign` или
`RAG_DATA_DIR`; база дня — `day-22.sqlite`. Общий `campaign.sqlite` учитывает
бюджет $1 для серии и кеш эмбеддингов. Все сайты используют один каталог.
Тексты запросов и найденный контекст передаются OpenAI; ключ в браузер не попадает.

## Результаты и выводы

Реальная серия 2026-10-05: 20 ответов, 15 816 входных и 1543 выходных токена,
оценка $0,00580560. Поисковые вопросы уже присутствовали в кеше индексации.
Точные входы, ответы, контекст и разбор каждого примера — в
[протоколе](results/experiment.json).

| Оценка | Без RAG | С RAG |
| --- | ---: | ---: |
| Найдено текстовых маркеров | 8/26 | 14/26 |
| Смысловая оценка | 0/20 | 12/20 |

Шкала смыслового разбора: 0 — нет ответа по проекту или ответ неверен;
1 — частичный; 2 — полный. Разбор выполнен агентом по сохранённым ответам и
источникам, это не независимая оценка пользователями. Нулевой балл честного
отказа означает отсутствие ответа, а не ошибочное поведение безопасности.

RAG верно объяснил память, паузу, сброс подтверждений и стратегии контекста.
Однако для профилей Дня 12, имён серверов и порядка инструментов Дня 20
нужные факты не попали в пять фрагментов. Для расписания найдено только
косвенное упоминание 09:00. В ответе об обезличивании модель смешала данные
интерфейса с данными, доступными модели. Значит, успех поиска нужного документа
10/10 ещё не означает наличие нужного доказательства или верный ответ.

Без RAG модель преимущественно признала отсутствие документов, иногда добавляя
общие догадки. Поэтому 8/26 найденных слов не отражают качество. Малый набор,
одна генерация на режим и экспертный разбор агентом ограничивают обобщение.
Локальные тесты проверяют различие контекстов, одинаковые инструкции, обработку
незавершённых ответов и защиту локального HTTP-интерфейса.

Минимальные проверки и браузерные действия: [протокол проверки](results/verification.md).

## Практическая польза

Сравнение полезно перед внедрением помощника по внутренним инструкциям:
оно показывает, какие вопросы требуют собственной базы и где теряется
информация. Просмотр точного контекста помогает отличить проблему поиска
от ошибки генерации и не улучшать модель вслепую.
