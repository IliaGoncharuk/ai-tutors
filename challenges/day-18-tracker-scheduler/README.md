# День 18 — утренняя аналитика задач

## Исходное задание

🔥 День 18. Планировщик и фоновые задачи

Сделайте MCP-инструмент с отложенным или периодическим выполнением.

Пример:

👉 reminder
👉 периодический сбор данных
👉 регулярный summary

Инструмент должен:

👉 сохранять данные (JSON / SQLite)
👉 выполняться по расписанию
👉 возвращать агрегированный результат

Результат:

Агент, который работает 24/7 и периодически выдаёт сводку (Давай в яндекс трекере. Хочу инструмент аналитики по задачам, чтобы утром показывал просроченные по дедлайну, те что сегодня должны быть закрыты)

## Теория

**Планировщик** решает, когда пора выполнить работу. **Фоновый исполнитель**
делает её независимо от открытого экрана. Таймер в браузере неудобен для таких
задач: вкладка может закрыться или быть приостановлена. Поэтому расписание
обычно хранится на диске, а работу выполняет отдельный процесс приложения.
Например, библиотека каждое утро считает книги, которые пора вернуть.

```text
Настройка → сохранённое расписание → проверка времени → исполнитель
                                                        ↓
Экран ← сохранённая сводка ← сбор данных и расчёт показателей
```

**Постоянное хранение** отделяет состояние от жизни процесса. После перезапуска
можно узнать расписание и результат последнего запуска. SQLite хранит данные
в локальной базе; транзакция объединяет изменения, которые должны примениться
согласованно. Например, резервирование запуска не должно оставлять половину
записи. [Атомарные транзакции SQLite](https://www.sqlite.org/atomiccommit.html),
[SQLite в Node.js](https://nodejs.org/api/sqlite.html).

**Повторное выполнение** требует явного правила. Проверка времени каждые несколько
секунд иначе запустит одну утреннюю задачу многократно. Уникальный ключ запуска
может включать дату и источник данных. Повторный запрос с этим ключом не создаёт
второй успешный результат. После сбоя полезны ограниченное число повторов и
пауза между попытками; бесконечные повторы могут перегрузить внешний сервис.
При аварии возможен повтор чтения API: это не обещание однократного сетевого вызова.

Расписание зависит от **часового пояса**, выходных и поведения при пропуске
времени. «Сегодня» в UTC и у пользователя может быть разными датами. Следует
заранее определить, нужно ли догонять пропущенные запуски и что означает такой
результат: текущие данные не позволяют восстановить точную вчерашнюю картину.
Непрерывная работа также требует непрерывно доступного компьютера и процесса.

## Решение

**Замысел.** Создать утреннюю панель назначенных пользователю задач Трекера.
Пользователь запускает приложение, сохраняет время и включает расписание.
По будням оно собирает сводку; при открытии сайта уже видны просроченные задачи,
сроки на сегодня и история выполнения. Проверить это можно отдельным запуском
таймера без HTTP-запроса и восстановлением сохранённого состояния после перезапуска.

**Устройство.** Один MCP-процесс содержит три инструмента:

- `schedule_digest` сохраняет источник, время и включение расписания;
- `run_digest_now` немедленно создаёт отдельную сводку;
- `get_digest` читает расписание, агрегаты, задачи и историю.

Фоновый исполнитель проверяет расписание каждые 5 секунд. По умолчанию выбраны
09:00, `Asia/Yekaterinburg`, будни; включение сохраняется кнопкой. При запуске
после этого времени в будний день формируется актуальная сводка. За одну дату
и источник допускается один успешный плановый результат. Изменение времени
не повторяет уже выполненный утренний запуск. Выходные пропускаются.
Ошибки видны в истории; до трёх попыток с задержками 1 и 5 минут.

Кнопка «Обновить сводку сейчас» перечитывает задачи, пересчитывает показатели
и сохраняет результат. Она использует сохранённый источник, не меняет расписание
и не закрывает задачи в Трекере. Старая успешная сводка остаётся доступной
при ошибке обновления; её дата и время явно показаны.

Читаются только назначенные владельцу токена задачи без резолюции. Просрочка —
`dueDate` раньше текущей даты; сегодняшний срок, отсутствие срока и неверная
дата учитываются отдельно. API считывается постранично; неполная выборка отклоняется.
Поддерживаемые поля и фильтры: [API Трекера](https://yandex.ru/support/tracker/ru/api/issues/search-issues).
Расчёты выполняются кодом; языковая модель не вызывается.

Нужен Node.js 22.13+. Из корня репозитория:

```powershell
npm.cmd --prefix challenges/day-18-tracker-scheduler ci
npm.cmd --prefix challenges/day-18-tracker-scheduler start
```

Сайт: [localhost:3018](http://localhost:3018). Для реального источника нужны
`YANDEX_TRACKER_TOKEN` и `YANDEX_TRACKER_ORG_ID` (или имеющиеся `YANDEX360_TOKEN`
и `YANDEX360_ORG`). Для облачной организации — `YANDEX_TRACKER_CLOUD_ORG_ID`.
Токену нужны права чтения. [Доступ к API](https://yandex.ru/support/tracker/ru/api/access).
Переключите источник, включите «По будням» и сохраните расписание.

База `scheduler.sqlite` находится в `~/.ai-tutors/tracker-lab-day-18/` вне Git.
Альтернативный каталог вне репозитория задаёт `TRACKER_LAB_DATA_DIR`.
Приложение запускается вручную: закрытая вкладка не мешает, остановка процесса,
сон или выключение компьютера останавливают выполнение. Ctrl+C завершает приложение.

```powershell
# Локальные проверки без внешнего API
npm.cmd --prefix challenges/day-18-tracker-scheduler run check
# Реальное чтение Трекера, сохранение и перезапуск; без OpenAI
npm.cmd --prefix challenges/day-18-tracker-scheduler run verify:live
```

## Результаты и выводы

27 сентября 2026 года прошли **7 тестов**, TypeScript и сборка. Реальный запуск
прочитал Трекер, сохранил сводку и восстановил её после закрытия и повторного
запуска всего приложения. Внешние записи и платные вызовы не выполнялись.
[Протокол](results/verification.md).

Для проверки расписания использованы вымышленные задачи из [domain.mjs](server/domain.mjs)
и контролируемое время: понедельник 08:59/09:00, повторный старт, вторник после
времени запуска и суббота. Отдельный настоящий таймер запустил сбор без HTTP.
[Точные сценарии](tests/scheduler.test.mjs). Это ускоренная проверка логики,
а не наблюдение непрерывной работы в течение суток. В текущем ручном режиме
24/7 возможно только при постоянно работающем приложении и компьютере.

## Практическая польза

Решение подходит для утренних отчётов, напоминаний и периодического сбора данных.
Сохранённая история позволяет отличить отсутствие просрочек от неудачного запуска,
а защита от повторов предотвращает дублирование одной сводки после перезапуска.
