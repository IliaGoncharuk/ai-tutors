# День 19 — композиция MCP-инструментов

## Исходное задание

🔥 День 19. Композиция MCP-инструментов

Создайте несколько MCP-инструментов, например:

👉 search
👉 summarize
👉 saveToFile

Реализуйте пайплайн:

👉 первый инструмент получает данные
👉 второй — обрабатывает
👉 третий — сохраняет результат

Проверьте:

👉 автоматическое выполнение цепочки
👉 корректность передачи данных между инструментами

Результат:

Автоматический пайплайн из нескольких MCP-инструментов

## Теория

**Композиция** связывает простые операции так, что результат одной становится
входом следующей. **Пайплайн**, или цепочка обработки, задаёт порядок этих
операций. Например, сервис погоды получает измерения, рассчитывает среднюю
температуру и сохраняет отчёт. Каждая стадия имеет отдельный проверяемый результат.

```text
Получить измерения → рассчитать показатели → сохранить отчёт
```

Для надёжной передачи данных нужен **контракт**: какие поля обязательны,
каков их тип и что они означают. Можно передавать весь объект, а можно его
идентификатор. Во втором случае исходные данные остаются в локальном хранилище,
а следующий инструмент получает точную ссылку на нужный снимок. Это уменьшает
сообщения и позволяет проверить происхождение результата.

**Снимок** фиксирует входные данные одного запуска. Если второй шаг заново
запросит внешний сервис, он может получить уже другую выборку. Поэтому важно
считать по тому набору, который получил первый шаг, и сохранять время сбора.
При этом постраничное API без транзакционного снимка не гарантирует, что внешний
сервис не изменялся во время самого чтения; такую границу следует описывать.

**Идемпотентность** означает, что повтор операции с тем же входом не создаёт
лишнего эффекта. Например, повторное сохранение одной сводки использует тот же
файл. Новый сбор данных создаёт новый снимок и новый отчёт. При ошибке середины
цепочки дальнейшие стадии обычно пропускают: сохранять «готовый» отчёт по
неуспешному расчёту нельзя. Частичные диагностические результаты полезно сохранить.

MCP стандартизует описания и вызовы инструментов, но порядок их выполнения
определяет приложение. Цепочка с заранее известными стадиями может работать
без языковой модели. [Описание инструментов MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

## Решение

**Замысел.** Создать локальную панель, в которой одна кнопка превращает задачи
Трекера в отчёт. Пользователь наблюдает три этапа, может раскрыть вход и результат
каждого, а затем прочитать сохранённый Markdown. Проверка связывает идентификаторы
между этапами и сравнивает показатели отчёта с рассчитанной сводкой.

**Устройство.** MCP-сервер предоставляет три инструмента:

| Шаг | Вход | Результат |
| --- | --- | --- |
| `search_issues` | Период `all` | Локальный снимок назначенных мне задач, его ID и количество строк |
| `summarize_issues` | ID снимка | Расчёт сроков по дате снимка, показатели, таблица и ID сводки |
| `save_report` | ID сводки | Markdown и JSON с одним содержимым, имена файлов |

Исполнитель автоматически вызывает инструменты именно в этом порядке через
настоящий MCP-клиент. При ошибке текущий шаг отмечается красным, дальнейшие
пропускаются. Сохранение одной сводки повторно использует те же имена файлов.
Для нового запуска создаются новые идентификаторы. Схема UUID и проверка имён
не позволяют передать произвольный путь вместо идентификатора.

Исходные данные — только назначенные владельцу токена задачи без резолюции.
Показатели включают просрочку, срок сегодня, будущие сроки, отсутствие и ошибку
даты. День определяется в `Asia/Yekaterinburg`. Все страницы API считываются;
выявленная неполнота отклоняется. [Поиск Трекера](https://yandex.ru/support/tracker/ru/api/issues/search-issues).

Нужен Node.js 22.13+. Из корня репозитория:

```powershell
npm.cmd --prefix challenges/day-19-mcp-pipeline ci
npm.cmd --prefix challenges/day-19-mcp-pipeline start
```

Сайт: [localhost:3019](http://localhost:3019). Учебные данные доступны сразу.
Для реального источника нужны `YANDEX_TRACKER_TOKEN` и `YANDEX_TRACKER_ORG_ID`
(поддерживаются `YANDEX360_TOKEN` и `YANDEX360_ORG`); для облачной организации
используется `YANDEX_TRACKER_CLOUD_ORG_ID`. Требуется чтение Трекера.
[Доступ к API](https://yandex.ru/support/tracker/ru/api/access).
OpenAI не используется. Остановка приложения — Ctrl+C.

Снимки и отчёты сохраняются вне Git в `~/.ai-tutors/tracker-lab-day-19/`.
Каталог можно изменить через `TRACKER_LAB_DATA_DIR`, но нельзя направить внутрь
репозитория. Кнопка «Показать Markdown» читает уже записанный отчёт.

```powershell
# Локальные тесты, типы и сборка
npm.cmd --prefix challenges/day-19-mcp-pipeline run check
# Настоящее чтение Трекера и запись локального отчёта
npm.cmd --prefix challenges/day-19-mcp-pipeline run verify:live
```

## Результаты и выводы

27 сентября 2026 года реальная цепочка завершила все три MCP-вызова и сохранила
оба файла. Модель не вызывалась. Прошли **6 тестов**, TypeScript и сборка.
[Технический протокол](results/verification.md).

Синтетический сценарий содержит 6 активных задач: 2 просроченных, 2 на сегодня,
1 будущую и 1 без дедлайна. Данные — [demoIssues](server/domain.mjs).
Проверка подтверждает передачу ID снимка во второй шаг, ID сводки в третий,
совпадение всех чисел JSON с расчётом и наличие ожидаемой просрочки в Markdown.
Отдельно искусственно вызвана ошибка расчёта: сохранение не запускалось.
[Точные проверки](tests/pipeline.test.mjs).

Результат доказывает исполнение фиксированной цепочки. Выбор произвольного
порядка моделью не проверяется в этом задании. Рабочие задачи и отчёты
в публичные результаты не включены; API Трекера не предоставляет здесь
транзакционного снимка всей изменяющейся выборки.

## Практическая польза

Такой подход подходит для регулярных отчётов, обработки выгрузок и сверки данных.
Разделение на этапы делает видимым место ошибки и позволяет независимо проверить,
какие исходные данные привели к конкретному сохранённому результату.
