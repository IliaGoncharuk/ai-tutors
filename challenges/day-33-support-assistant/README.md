# День 33. Ассистент поддержки пользователей

## Исходное задание

День 33. Ассистент поддержки пользователей

Сделайте мини-сервис для поддержки пользователей.

Ассистент должен:

👉 отвечать на вопросы о продукте
👉 использовать RAG (FAQ, документация)
👉 учитывать контекст пользователя или тикета

Через MCP:

👉 подключите CRM
👉 или JSON с пользователями / тикетами

Пример:

👉 «Почему не работает авторизация?»
👉 ассистент отвечает с учётом данных тикета

Результат:

AI-ассистент для поддержки пользователей

## Теория

**Поддержка пользователей** соединяет общие сведения о продукте с конкретной
ситуацией человека. Одинаковая фраза «не могу войти» может означать
неподтверждённую регистрацию, временную блокировку, истечение сессии или
неизвестную техническую проблему. Ответ из одного FAQ без контекста способен
предложить верный совет не тому пользователю.

**База знаний** содержит правила продукта: значения кодов ошибок, условия
доступа и порядок восстановления. **Тикет** — отдельное обращение: наблюдения,
сообщение пользователя, статус обработки и связь с учётной записью.
**CRM** (система управления взаимодействием с клиентами) или более простое
хранилище содержит эти записи. Правило из справочника и наблюдение из тикета
нельзя смешивать: «код X означает блокировку» не доказывает, что у текущего
пользователя был именно код X.

**RAG** сначала находит подходящие разделы справочника и только затем передаёт
их языковой модели. Эмбеддинги помогают сопоставить разговорную формулировку
с термином документации. Например, «меня выкинуло из старой вкладки» может
соответствовать разделу об истёкшей сессии. Код ошибки, если он известен,
уточняет поиск и уменьшает неоднозначность.
[OpenAI: embeddings](https://developers.openai.com/api/docs/guides/embeddings).

**MCP** отделяет получение данных от формулирования ответа. Клиент вызывает
инструмент чтения обращения, получает связанные сведения о пользователе и
передаёт их в контекст. Разрешения должны ограничивать не только список
операций, но и область записей. Возможность прочитать одного клиента не должна
автоматически открывать всех остальных.
[MCP: инструменты](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

```text
Вопрос + выбранное обращение
        ↓
Факты тикета и пользователя → поиск подходящего FAQ
        ↓
Объяснение причины + допустимые шаги + недостающие сведения
```

**Неопределённость** — нормальный результат диагностики. Если известен только
симптом, нельзя объявлять причину установленной. Помощник должен отличать
«это подтверждено кодом ошибки» от «это возможный вариант» и запросить
сведения, которые действительно помогут различить причины. При временной
блокировке без времени последней попытки нельзя вычислить оставшееся время.
При этом пароль и токен не нужны для обычного уточнения симптомов.

**Консультация и действие** — разные возможности. Ответ «запросите письмо» не
означает, что программа отправила письмо; инструкция по восстановлению не
меняет пароль. Отчёт должен подтверждать реальные операции инструментов.
Проверка качества поэтому включает применение контекста, отсутствие смешения
пользователей, соответствие инструкции FAQ и честный отказ от неподтверждённых
объяснений.

## Решение

Замысел — сделать маленькую локальную службу поддержки, где можно выбрать
обращение и увидеть, почему один и тот же вопрос требует разных ответов.
Человек выбирает тикет, задаёт вопрос, затем проверяет консультацию по
показанным FAQ и MCP-данным. Проверка использует четыре случая, включая
обращение без установленной причины.

TutorDesk — вымышленный учебный продукт. В `data/support.json` находятся только
синтетические идентификаторы и состояния, без имён, адресов и настоящих
учётных записей. `faq.md` и `policy.md` описывают именно этот вымышленный продукт,
а не универсальные правила авторизации. Например, блокировка на 15 минут —
условие примера, не стандарт для любых сервисов.

Node.js запускает настоящий MCP-сервер с инструментами `get_ticket` и
`get_user`. Связь с тикетом фиксируется при создании процесса: у модели нет
параметра для чтения другого пользователя. Приложение само вызывает обе
операции, добавляет их результаты к RAG-контексту и получает консультацию от
`gpt-5.6-luna`. Корпус FAQ индексируется `text-embedding-3-small`, 512 измерений.
Пользователи и тикеты не включаются в общий индекс.

Из папки задания:

```powershell
npm.cmd ci
npm.cmd start
```

Команды устанавливают зависимости и запускают сайт
[127.0.0.1:3033](http://127.0.0.1:3033). Обновите базу, выберите тикет и выполните
вопрос. `OPENAI_API_KEY` задаётся окружением сервера; ключ не вводится на сайте.
«Открыть сохранённый пример» последовательно показывает записанные ответы
без новых расходов. Остановка сервера — Ctrl+C.

`npm.cmd run check` проверяет приложение локально;
`npm.cmd run experiment` делает четыре настоящих платных запроса.
FAQ, вопрос и сведения выбранного учебного тикета передаются в OpenAI.
Каталог и общий бюджет $1 — по [ADR серии](../../docs/decisions/0019-days-31-35-project-assistants.md).
Сервис только читает записи: изменение аккаунтов, отправка писем и закрытие
тикетов не реализованы.

## Результаты и выводы

Исходные данные — [`support.json`](data/support.json), справочник —
[`faq.md`](data/faq.md). В контрольной серии всем четырём тикетам задаётся
дословно «Почему не работает авторизация? Что мне сделать?».
Полные ответы, использованные фрагменты и MCP-данные сохраняются в
[`results/experiment.json`](results/experiment.json). Проверка от 2026-10-18:
прошли 6 локальных тестов и синтаксис; браузер показал сохранённый ответ,
пять фрагментов FAQ/политики и два настоящих MCP-вызова.

Модель различила все четыре случая: предложила подтвердить адрес, подождать
после блокировки, войти заново при истёкшей сессии и уточнить неизвестную
ошибку. Для блокировки явно отказалась вычислять оставшееся время без данных.
Это ручная оценка четырёх фиксированных примеров, не статистическая оценка
качества поддержки. В серии 9 API-вызовов с индексом, расчётно $0,00161309;
общий расход дней 31–33 $0,01543221, незакрытых резервов нет.

Корректное чтение нужного пользователя ещё не доказывает качество совета.
Это проверяется по тексту ответа. Номера цитат валидируются автоматически;
их смысловое соответствие остаётся отдельной оценкой. Настоящая CRM,
авторизация операторов и реальные персональные данные не используются.

## Практическая польза

Подход помогает составлять первые ответы поддержки с учётом состояния
обращения. Оператор видит происхождение диагноза, может исправить неверное
предположение и передать сложный случай человеку, не заставляя пользователя
повторять уже известные факты.
