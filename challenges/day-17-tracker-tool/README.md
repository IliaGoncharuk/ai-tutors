# День 17 — первый инструмент Яндекс Трекера

## Исходное задание

🔥 День 17. Первый инструмент MCP

Реализуйте свой MCP-сервер вокруг любого API (Яндекс.Трекер)

Сделайте:

👉 регистрацию инструмента
👉 описание входных параметров
👉 возврат результата

Подключите инструмент к своему агенту и:

👉 вызовите его из приложения
👉 получите и используйте результат

Результат:

Агент делает вызов к MCP-инструменту и получает результат

## Теория

**API** — программный интерфейс сервиса. **MCP-инструмент** — описанная через
протокол операция, которая может обращаться к API, базе данных или локальному
вычислению. MCP задаёт способ обнаружения и вызова, но бизнес-логику пишет
разработчик сервера. Например, инструмент `find_books` принимает жанр и возвращает
список книг из библиотечного API.

Регистрация инструмента связывает имя, понятное описание, схему входных данных
и обработчик. Схема ограничивает форму запроса; обработчик проверяет прикладные
условия. Подсказка «только чтение» описывает намерение, но настоящую границу
обеспечивают реализованные операции и права API-токена.
[Инструменты MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

**Вызов функции моделью** проходит несколько шагов. Модель видит описания
доступных операций и предлагает имя с аргументами. Приложение проверяет предложение,
вызывает инструмент и возвращает разрешённую часть результата модели. После этого
она формирует ответ. Модель не выполняет произвольный код самостоятельно и не
получает ключ внешнего сервиса.
[Function calling](https://developers.openai.com/api/docs/guides/function-calling).

```text
Запрос → модель выбирает инструмент → приложение проверяет параметры
       → MCP → API → результат → разрешённые данные → ответ модели
```

**Минимизация данных** означает передачу только того, что нужно для конкретной
задачи. Для фразы «просрочено пять задач» достаточно числа; тексты и авторы не нужны.
Проекция по списку разрешённых полей надёжнее удаления нескольких известных
секретных полей: новые поля исходного ответа также останутся за границей.
Агрегаты позволяют объяснить общую картину, но не причины задержки конкретной задачи.

API часто возвращает результаты страницами. Первая страница не равна всей выборке:
агрегирование нужно выполнять после получения всех страниц либо явно сообщать
о неполноте. Трекер предоставляет параметры страниц и заголовки с количеством
результатов. [Поиск задач](https://yandex.ru/support/tracker/ru/api/issues/search-issues).

## Решение

**Замысел.** Сделать сайт, где пользователь выбирает запрос о собственных задачах,
а агент обращается к Трекеру через зарегистрированный MCP-инструмент. Сайт показывает
таблицу задач и путь вызова; модель объясняет только числовые показатели. Результат
проверяется реальным соединением, контролем передаваемых данных и коротким API-прогоном.

**Устройство.** Инструмент `search_issues(period)` принимает `all`, `overdue` или
`today`. Сервер читает задачи по условию `Assignee: me() Resolution: empty()`,
обрабатывает страницы и сравнивает `dueDate` с датой в `Asia/Yekaterinburg`.
Незавершённость определяется отсутствием резолюции, а не названием статуса.
Просроченные имеют срок раньше сегодняшней даты; срок сегодня выделяется отдельно.
Задачи без срока и с некорректной датой не считаются просроченными.

Интерфейс предлагает три фиксированных запроса: так произвольный личный текст
также не уходит в модель. Источник (`Учебные данные` / `Мой Яндекс Трекер`)
выбирается независимо от исполнения (`Демонстрация без модели` / настоящий агент).
В демонстрации решение о вызове принимает код, но MCP-соединение настоящее.
В реальном режиме GPT-5.6 Luna выбирает инструмент и получает только семь чисел.
Названия, ключи, ссылки и исходный JSON не передаются в OpenAI; ответ модели
не может объяснять содержание отдельных задач.

Нужен Node.js 22.13+. Из корня репозитория:

```powershell
npm.cmd --prefix challenges/day-17-tracker-tool ci
npm.cmd --prefix challenges/day-17-tracker-tool start
```

Сайт: [localhost:3017](http://localhost:3017). Для Трекера задайте в окружении
`YANDEX_TRACKER_TOKEN` и `YANDEX_TRACKER_ORG_ID`; поддерживаются существующие
`YANDEX360_TOKEN` и `YANDEX360_ORG`. Для облачной организации вместо обычного ID
используется `YANDEX_TRACKER_CLOUD_ORG_ID`. Нужны права чтения Трекера.
[Авторизация](https://yandex.ru/support/tracker/ru/api/access).
Для настоящего агента нужен `OPENAI_API_KEY`. Значения ключей не вводятся в браузер.

Результаты сохраняются вне Git в `~/.ai-tutors/tracker-lab-day-17/`.
`TRACKER_LAB_DATA_DIR` задаёт альтернативный каталог вне репозитория.
Приложение не изменяет задачи. Остановка — Ctrl+C в терминале.

```powershell
# Тесты, проверка типов и сборка без платных вызовов
npm.cmd --prefix challenges/day-17-tracker-tool run check
# Реальные Трекер и OpenAI; расходует согласованный бюджет
npm.cmd --prefix challenges/day-17-tracker-tool run verify:live
```

Проверочные скрипты серии используют общий журнал бюджета вне Git. Каждый
API-запрос предварительно резервирует $0,05 из $1, включая неуспешные попытки.
Это консервативный локальный предел, не баланс аккаунта. Оценка стоимости учитывает
вход по $0,25 и выход по $1,20 за миллион токенов: вход взят с запасом на cache writes.
[Тариф модели](https://developers.openai.com/api/docs/models/gpt-5.6-luna).

## Результаты и выводы

27 сентября 2026 года реальный запрос «Покажи общую сводку моих незавершённых задач.»
выполнил один вызов `search_issues` через MCP и два обращения к модели:
**681 входной и 87 выходных токенов**, оценка **$0,00027465**. Проверено,
что модель получила числовую проекцию результата. Рабочие задачи и их количества
не публикуются в репозитории; публичный протокол содержит только техническую проверку.

Прошли 6 тестов, TypeScript и сборка. Синтетический сценарий содержит 6 активных
задач: 2 просроченные, 2 на сегодня, 1 будущую и 1 без срока; закрытая задача
исключается. Даты вычисляются относительно выбранного дня. Точные данные —
[demoIssues](server/domain.mjs), проверки — [tests](tests/agent.test.mjs), итог —
[протокол](results/verification.md). Подменённый ответ модели в тесте доказывает
маршрутизацию и границу данных, но не качество реальной модели.

## Практическая польза

Такой адаптер превращает внешний API в понятный агенту инструмент. Он позволяет
строить помощников по срокам, сохраняя подробные рабочие данные на компьютере
и независимо проверяя точность числовой сводки.
