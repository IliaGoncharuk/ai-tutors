# День 28. Локальная LLM + RAG

## Исходное задание

👉 скорость

## Теория

**RAG** — генерация ответа с дополнительным поиском по коллекции документов. Сначала система ищет небольшое число фрагментов, относящихся к вопросу. Затем передаёт эти фрагменты модели вместе с вопросом. Модель может опираться на содержание базы, которого нет в её общих знаниях. Поиск выбирает свидетельства; генерация формулирует ответ. Ошибки на любом этапе влияют на итог.

Текст обычно делят на **фрагменты** (chunks), чтобы не передавать модели всю коллекцию сразу. Метаданные фрагмента — источник, заголовок и идентификатор — позволяют показать происхождение результата. Слишком короткие фрагменты теряют связи между соседними предложениями; слишком длинные могут включить много лишнего текста.

**Векторный поиск** превращает вопрос и документы в числовые векторы (эмбеддинги) и ранжирует их по геометрической близости. Векторы разных моделей не взаимозаменяемы: если индекс рассчитан одной embedding-моделью, запрос нужно преобразовать той же моделью и с той же размерностью. Получение вектора запроса через облако означает, что часть RAG-пайплайна выходит за пределы устройства.

**Лексический поиск** сопоставляет слова вопроса со словами документов и может ранжировать документы по частоте и редкости совпадений, как в семействе BM25. Он не требует embedding-модели и может полностью работать с локальным текстом, но обычно хуже находит перефразированные понятия без общих слов. В этой лаборатории поиск основан на сохранённых текстовых фрагментах и локальном TF/IDF-подобном ранжировании; старые векторы не используются.

Сравнение локальной и облачной генерации имеет смысл, только если для обоих ответов совпадают вопрос, найденные фрагменты, инструкция и параметры. Скорость измеряется задержкой отдельного вызова. Качество нужно оценивать по заранее выбранным ожиданиям и источникам, а не только по длине или уверенности ответа. Стабильность требует повторов одного сценария; результаты единичного запуска не позволяют делать общий вывод.

## Решение

**Замысел.** Локальная веб-лаборатория берёт сохранённые документы и контрольные вопросы предыдущего RAG-задания. Пользователь видит найденные фрагменты, вызывает локальную модель и при желании отдельно отправляет тот же вопрос и тот же контекст облачной модели. Панель показывает задержки, контрольные слова и точные источники, а JSON-протокол позволяет сохранить результаты.

**Устройство.** В папке лежит снимок `index.json.gz` задания Дня 21, содержащий фрагменты корпуса и исходные векторы. Поскольку исходные векторы рассчитаны облачной моделью, локальный поиск использует текст фрагментов и простое BM25-подобное лексическое ранжирование. Оно не делает облачных embedding-запросов. При генерации LM Studio получает только вопрос и пять лучших локально найденных фрагментов. Облачная кнопка использует OpenAI Chat Completions API, передавая ключ из серверного окружения; ключ не попадает в браузер ([официальная документация API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)). Офлайн-замер retrieval повторяется командой `npm run experiment:retrieval` и сохраняет точные ранги в `results/retrieval-check.json`.

Нужны Node.js 22.13+ и локальная модель с запущенным сервером LM Studio. Для облачного сравнения дополнительно настройте `OPENAI_API_KEY`; модель по умолчанию `gpt-5.6-luna` переопределяется через `OPENAI_MODEL`. Из папки задания выполните `npm start`, затем откройте `http://127.0.0.1:3028`. Выберите контрольный вопрос, найдите контекст и запускайте локальную или облачную генерацию отдельными кнопками. Облачный вызов может быть платным; он не запускается автоматически.

## Результаты и выводы

Сохранённый архив содержит 264 фрагмента двух стратегий; поиск использует 94 фрагмента фиксированного размера и 512-мерные векторы только хранит в архиве. На десяти контрольных вопросах локальный поиск нашёл ожидаемый документ в top-5 для **9/10** вопросов и покрыл **23/26** контрольных слов. Среднее время поиска на Windows x64 с Node.js 24.14.0 и 20 логическими процессорами — **4,996 мс**; это только лексический retrieval, не время генерации. Вопрос о трёх стратегиях Дня 10 не нашёл ожидаемый README в top-5: общие слова «стратегии» и «контекст» привели к другим документам. Полные ранги — в [протоколе retrieval](results/retrieval-check.json).

Реальный запуск модели и сравнение генерации пока не выполнены: в рабочем окружении LM Studio не подтвердила доступность локального API. Поэтому значения качества ответов, скорости генерации и стабильности не создавались. Интерфейс показывает текущие измерения и сохраняет ответы только после реальных запусков.

Контроль слов — лишь эвристика покрытия ожидаемого ответа. Она не подтверждает фактическую правильность. Чтобы оценить стабильность, вручную повторите один вопрос несколько раз и сравните сохранённые протоколы. Различие поискового этапа с исходной векторной лабораторией также нужно учитывать при выводах.

## Практическая польза

Такой локальный RAG полезен для поиска по закрытым внутренним материалам, когда содержимое вопроса и документов не должно покидать сеть. Параллельный облачный режим помогает сравнить качество, но передаёт выбранные тексты провайдеру и может тарифицироваться отдельно.
