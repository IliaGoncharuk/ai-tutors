# День 21 — индексация документов

## Исходное задание

🔥 День 21. Индексация документов

Возьмите набор документов:

👉 README / статьи / код / pdf → текст
👉 минимум 20–30 страниц текста суммарно (или эквивалент в коде)

Реализуйте пайплайн индексации:

👉 разбиение на чанки (chunking)
👉 генерация эмбеддингов
👉 сохранение индекса (FAISS / SQLite / JSON)

Усиление:

👉 добавьте метаданные к каждому чанку (source, title/file, section, chunk_id)
👉 сделайте минимум 2 стратегии chunking и сравните их:

- по фиксированному размеру
- по структуре (заголовки/разделы/файлы)

Результат:

Локальный индекс документов с эмбеддингами + метаданные + сравнение 2 стратегий chunking

## Теория

**Индексация** подготавливает документы к быстрому поиску. Сначала из формата
хранения извлекают текст и сохраняют его происхождение. Затем текст делят на
небольшие фрагменты — **чанки**. Для каждого фрагмента вычисляют представление,
по которому его можно сопоставить с вопросом. Сам индекс связывает эти
представления с исходными текстами и их адресами.

**Эмбеддинг** — вектор чисел, вычисленный обученной моделью. Близкие по смыслу
тексты должны иметь близкие векторы: вопрос «когда открывается библиотека?»
может найти «режим работы читального зала» без точного совпадения слов.
Вектор не является кратким пересказом, и отдельное его число не означает
конкретный человеческий признак. Для вопроса и документов используют одну
модель и размерность: представления разных моделей несопоставимы.
[Официальное объяснение эмбеддингов](https://developers.openai.com/api/docs/guides/embeddings).

**Косинусное сходство** сравнивает направления векторов: скалярное произведение
делят на произведение их длин. Большая оценка означает большую близость в
данном пространстве, но не вероятность правильного ответа. Алгоритм может
найти тематически похожий документ, в котором нет нужного факта.

**Границы фрагментов** влияют на поиск. Маленький фрагмент точнее соответствует
одной мысли, но может потерять пояснение. Большой сохраняет окружение, однако
смешивает темы и занимает больше места в контексте языковой модели. Разбиение
фиксированной длины предсказуемо, но способно разделить предложение или таблицу.
Структурное разбиение следует заголовкам; слишком длинный раздел всё равно
нужно делить. **Перекрытие** повторяет край предыдущего фрагмента в следующем,
уменьшая потерю связи ценой дублирования и дополнительных эмбеддингов.

```text
Справочник → раздел «Время работы» → фрагмент + вектор + адрес
Вопрос    → вектор                → сравнение → нужный фрагмент
```

**Метаданные** отвечают на вопросы «откуда это?» и «как найти оригинал?».
Название файла удобно человеку, стабильный идентификатор удобен программе,
а раздел и координаты позволяют проверить цитату. Изменение текста или модели
должно создавать новую версию индекса: иначе найденный вектор может указывать
на уже другой документ. Постоянное хранение позволяет использовать результат
после перезапуска. SQLite поддерживает атомарные транзакции: новый индекс можно
заменить целиком, сохранив предыдущий при ошибке подготовки.
[Транзакции SQLite](https://www.sqlite.org/atomiccommit.html).

## Решение

**Замысел.** Создать локальный стенд, на котором человек увидит путь от
документа к результатам поиска. Он выбирает стратегию, рассматривает границы
фрагментов, строит индекс и задаёт вопрос. Сравнение на одних документах и
вопросах показывает, влияет ли способ разбиения на обнаружение нужного источника.
Проверка состоит из сохранения и повторного чтения индекса и поиска ответных
документов для десяти заранее подготовленных вопросов.

**Корпус.** В [data/corpus.json](data/corpus.json) зафиксированы README дней 1–20
на 5 октября 2026 года. Удалены разделы с точным заголовком `## Исходное задание`;
старые README с другими заголовками сохранены целиком. Переносы строк
приведены к LF; теория, реализация и результаты сохранены. Получилось 20
документов, 18 628 слов. Условная страница принята равной 500 словам: 37,3
страницы. Это явно выбранная мера объёма, а не число страниц PDF.
Сайт не читает произвольные файлы компьютера. Снимок автономен от исходных папок.

**Устройство.** Сервер Node.js хранит SQLite, браузер React показывает документы,
фрагменты и результаты. Фиксированное окно — 1800 символов, шаг — 1600.
Структурная стратегия разделяет по Markdown-заголовкам; длинные разделы делятся
таким же окном. Заголовки внутри ограждённых блоков кода не учитываются; Setext-заголовки
и вложенные HTML-блоки этот небольшой парсер не разбирает.
Для каждого фрагмента сохраняются `source`, `title`, `section`, `chunk_id`,
начало и конец в снимке. Текст эмбеддинга включает название, раздел и фрагмент.
Модель — `text-embedding-3-small`, размерность — 512; поиск — точный перебор
косинусного сходства. Для такого небольшого корпуса отдельный векторный сервер
не требуется. [API эмбеддингов](https://developers.openai.com/api/docs/guides/embeddings).

Готовый реальный индекс находится в [data/index.json.gz](data/index.json.gz):
при первом запуске он импортируется в SQLite. Просмотр разбиения и результатов
не требует API. Новый поисковый вопрос создаёт его эмбеддинг через API;
повторный текст использует общий кеш. Ключ `OPENAI_API_KEY` нужен только серверу.

Нужен Node.js 22.13+. Из этой папки:

```powershell
npm.cmd ci              # установить зависимости
npm.cmd start           # открыть сервер http://127.0.0.1:3021
npm.cmd run check       # тесты, типы и сборка без платных запросов
npm.cmd run experiment  # повторить реальное сравнение через API
```

Остановка — Ctrl+C. Рабочие данные: `~/.ai-tutors/rag-campaign`, другое место
задаётся `RAG_DATA_DIR`. База дня — `day-21.sqlite`, общий кеш и бюджет —
`campaign.sqlite`. Общий лимит пяти сайтов — $1, неизвестный расход сохраняется
резервом; автоматических повторов запросов нет. Изменение каталога создаёт
отдельный журнал, поэтому все пять приложений нужно запускать с одним каталогом.
Индекс локальный, но текст эмбеддингов отправляется OpenAI.

## Результаты и выводы

Реальный эксперимент 2026-10-05: модель `text-embedding-3-small`, две стратегии,
одинаковые [10 вопросов с эталонными источниками](data/questions.json).
Для каждого вопроса проверяется, присутствует ли ожидаемый документ среди
первых пяти результатов. Это **source hit@5**, не правильность ответа модели.
Все тексты результатов и оценки сохранены в [протоколе](results/experiment.json).

| Стратегия | Фрагментов | Ожидаемый документ в top-5 |
| --- | ---: | ---: |
| Фиксированная длина | 94 | 10/10 |
| Заголовки и разделы | 170 | 10/10 |

С учётом диагностического прогона: 35 API-вызовов, 141 442 входных токена,
оценка расхода $0,00282884. В число входят
обе индексации и эмбеддинги десяти вопросов; вопросы второй стратегии взяты из
кеша. После исключения комментариев внутри блоков кода из заголовков обе
стратегии нашли источники 10/10. Структурный вариант создал больше фрагментов. Это небольшая выборка: вывод нельзя переносить на любой корпус.
Идентичность текстовых цитат и качество генерации здесь ещё не оцениваются.

Локальные тесты проверяют покрытие исходного текста, стабильность координат,
восстановление SQLite, сохранность индекса при сбое, общий бюджет и кеширование.

Минимальные проверки и браузерные действия: [протокол проверки](results/verification.md).

## Практическая польза

Такой индекс служит основой поиска по инструкциям команды, справочникам или
документации продукта. Видимые фрагменты позволяют заметить плохое извлечение
текста и потерянные заголовки до подключения языковой модели. Сохранённые
координаты и версия корпуса позволяют воспроизвести и объяснить результат поиска.
