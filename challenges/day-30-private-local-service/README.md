# День 30. Локальная LLM как приватный сервис

## Исходное задание

День 30. Локальная LLM как приватный сервис

Разверните локальную LLM как сервис:

👉 на VPS или домашнем сервере
👉 с HTTP API
👉 с возможностью чата

Проверьте:

👉 доступ к модели по сети
👉 стабильность при нескольких запросах
👉 базовые ограничения (rate limit / max context)

Результат:

Приватный AI-сервис на базе локальной LLM

## Теория

Модельный сервис принимает запросы по сети, загружает или использует уже загруженные веса и возвращает результаты генерации. **Привязка адреса** определяет, кто может установить соединение. `127.0.0.1` доступен только с этого компьютера; `0.0.0.0` прослушивает сетевые интерфейсы, поэтому запросы могут приходить с других устройств.

Сетевой доступ требует больше контроля, чем локальный вызов. **Аутентификация** проверяет право клиента обращаться к API. **Ограничение частоты** снижает риск перегрузки и бесконечных циклов. **Ограничение контекста** защищает память и время ответа от чрезмерно длинных запросов. Ограничение числа параллельных вычислений помогает оставить ресурсы другим задачам.

Домашняя Wi-Fi сеть не равна зашифрованному доверенному каналу: в одной сети могут быть устройства гостей или вредоносные программы. Для постоянно используемого сервиса нужны TLS, безопасное управление секретами, обновления и сетевые правила. Небольшая учебная проверка на домашней сети не заменяет эксплуатационную оценку безопасности.

Число запросов в минуту и размер контекста — разные ограничения. Rate limit считают по времени и клиенту; лимит контекста относится к одной беседе. Нагрузка при нескольких запросах зависит от модели, памяти, CPU/GPU и числа одновременных генераций. Поэтому стабильность проверяют несколькими параллельными и последовательными вызовами, записывая ошибки и задержку.

## Решение

**Замысел.** Домашний компьютер запускает Node.js сервис с чатом и HTTP API. Другие устройства домашней сети обращаются к нему по адресу компьютера в Wi-Fi. Сам сервер LM Studio остаётся привязан к локальному компьютеру; Node.js проверяет токен пользователя и проксирует разрешённые сообщения. Встроенные пределы позволяют проверить слишком частые, слишком длинные и параллельные запросы.

**Устройство.** Приложение слушает `0.0.0.0:3030`; API требует `DAY30_SERVICE_TOKEN` длиной не менее 24 символов. Соединение с LM Studio идёт на `127.0.0.1:1234`; при включённой авторизации LM Studio токен задаётся в `LM_STUDIO_TOKEN`. Действуют пределы 12 запросов в минуту с одного IP, 2 одновременно выполняемых запроса с одного IP, 20 сообщений, около 12 000 символов текста, контекстное окно по умолчанию 8192 токена и 512 выходных токенов. Для контекстной проверки сервер использует грубую оценку 3 символа на токен, затем передаёт настоящий `context_length` локальному API. Оценка может отличаться от токенизатора модели.

Официальная документация LM Studio отдельно предупреждает, что сетевой адрес открывает API для других устройств и рекомендует включить аутентификацию ([доступ в локальной сети](https://lmstudio.ai/docs/developer/core/server/serve-on-network), [настройки API-сервера](https://lmstudio.ai/docs/developer/core/server/settings)). В этой конфигурации LM Studio наружу не публикуется: наружу доступен только ограниченный сервис-обёртка.

Нужны Node.js 22.13+ и загруженная локальная модель. В PowerShell из папки задания сгенерируйте токен для текущего процесса и скопируйте его из терминала в поле браузера:

```powershell
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$bytes = New-Object byte[] 32
$rng.GetBytes($bytes)
$token = [BitConverter]::ToString($bytes).Replace('-', '')
$rng.Dispose()
$env:DAY30_SERVICE_TOKEN = $token
$token # показать только что созданный токен для ввода в браузере
npm.cmd start
```

Значение не сохраняйте в репозитории. `SERVICE_CONTEXT_TOKENS` меняет контекстный предел (1024–131072; по умолчанию 8192). Откройте с телефона/другого компьютера `http://<IP-компьютера>:3030`. IP компьютера можно найти командой `ipconfig`; используйте адрес Wi-Fi адаптера. Для локальной модели включите в LM Studio локальный API-сервер. Не публикуйте порт через маршрутизатор и остановите приложение после проверки.

## Результаты и выводы

Сервер и интерфейс подготовлены, но реальную доступность с другого домашнего устройства проверить из среды разработки невозможно. Понадобится открыть адрес компьютера с телефона или другого ПК, выполнить несколько диалогов и проверить ответ 401 без токена, отказ при превышении размера и частоты, поведение двух параллельных запросов. Брандмауэр Windows или изоляция Wi-Fi клиентов могут блокировать соединение; это отдельная настройка сети, которую приложение не меняет.

Сервис ограничивает вход и выход, но учебная конфигурация не включает HTTPS и не предназначена для публикации в интернете. Не передавайте по такой сети чувствительные данные.

## Практическая польза

Домашний API позволяет использовать более мощный компьютер с моделью как локальную точку генерации для устройств той же сети. Чёткие ограничения упрощают оценку поведения при нескольких запросах и помогают понять, что ещё потребуется для постоянно используемого сервиса.
