# День 13 — состояние задачи

## Исходное задание

🔥 День 13. Состояние задачи (Task State Machine)

Реализуйте состояние задачи как конечный автомат:

👉 этап задачи

👉 текущий шаг

👉 ожидаемое действие

Пример состояний:

👉 planning → execution → validation → done

Проверьте:

👉 паузу на любом этапе

👉 продолжение без повторных объяснений

Результат:

Агент с формализованным состоянием задачи

## Теория

**Конечный автомат** описывает процесс через конечный набор состояний
и переходов между ними. Состояние отвечает на вопрос «где процесс сейчас»,
событие — «что произошло», переход — «куда после этого можно перейти».
Например, документ проходит этапы «черновик → редактура → готов»;
событие «найдены ошибки» возвращает его из редактуры в черновик.
Эти базовые понятия формализованы в
[стандарте W3C SCXML](https://www.w3.org/TR/scxml/#BasicStateMachineNotation).

| Понятие | Назначение | Пример для документа |
| --- | --- | --- |
| Этап | Крупная фаза процесса | Редактура |
| Текущий шаг | Конкретная работа внутри этапа | Проверить подписи к рисункам |
| Ожидаемое действие | Что должно произойти дальше | Автор исправляет две подписи |
| Событие | Уже произошедшее действие | Автор отправил исправления |

Этапов может быть мало, а задач и значений полей — много. Текст документа,
найденные замечания и текущий шаг относятся к данным процесса: не нужно
создавать отдельное состояние автомата для каждого возможного текста.
Так структура остаётся понятной, а сведения для продолжения — достаточно
подробными.

**История** показывает, как процесс пришёл к текущему положению, а **состояние**
фиксирует его актуальный результат. Переписка «планировали проверить подписи»
не сообщает однозначно, сделана ли проверка и что осталось. Явная запись
этапа и следующего действия устраняет необходимость каждый раз угадывать
это по сообщениям. Журнал событий полезен для объяснения изменений, но его
не следует путать с текущей карточкой задачи.

Пауза — ещё одно измерение состояния. Можно помнить одновременно
«этап: редактура» и «приостановлено: да». Продолжение снимает паузу,
сохраняя этап, шаг и подготовленные материалы. Если вместо этого заменить
этап единственным значением «пауза», придётся отдельно помнить, куда вернуться.
Для восстановления после закрытия программы сохраняют не только название
этапа, но и связанные данные.

Автомат управляет последовательностью действий, а не доказывает качество
результата. Переход в «готов» может означать лишь решение оператора завершить
работу. Чтобы требовать одобрения плана или пройденных проверок, нужны
дополнительные условия перехода и проверяемые свидетельства. Аналогично,
текст «всё проверено» от языковой модели сам по себе не является результатом
запущенного теста.

## Решение

**Замысел.** Создать локального помощника для подготовки проекта приложения,
у которого видна карточка текущей работы: этап, шаг, ожидаемое действие
и материалы. Пользователь может остановиться, закрыть сайт и позже продолжить
с того же места. Агент получает сохранённую карточку автоматически, поэтому
не нужно заново пересказывать достигнутый результат.

**Устройство.** Самостоятельный сайт на React и TypeScript с сервером Node.js
содержит чат, профили, три слоя памяти и панель состояния задачи.
Основной путь — `planning → execution → validation → done`:
планирование, подготовка результата, проверка, завершение. Из проверки можно
вернуться к подготовке результата для исправлений. Шаг и ожидаемое действие
редактируются явно; план и результат можно подготовить вручную или получить
кнопкой обращения к модели на соответствующем этапе. Результат работы здесь —
текстовая спецификация сервиса записи к репетиторам: цель, роли, бронирование,
отмена и критерии приёмки.

Пауза сохраняет текущий этап и блокирует изменение карточки, генерацию
материалов и ответы чата до продолжения. Новый диалог не сбрасывает состояние
задачи. Оно передаётся модели даже при отключении обычных слоёв памяти.
Текст замечаний модели на этапе проверки остаётся рекомендацией,
а не подтверждением корректности результата.

Состояния задач хранятся отдельно в `task-state.json`, с привязкой к задаче
и её профилю. Каталог данных — `~/.ai-tutors/memory-lab-day-13/` вне репозитория.
Согласованная версия файлов памяти и состояния публикуется одним указателем
`CURRENT.json`. Граф переходов есть уже в этой версии; одобрение плана
и доказательства валидации пока не являются условиями перехода.
Подробные правила — в [спецификации](../../docs/features/day-13-task-state.md).

Нужен Node.js 22.13 или новее. Из корня репозитория установите зависимости
и запустите сайт на [localhost:3013](http://localhost:3013):

```powershell
npm.cmd --prefix challenges/day-13-task-state ci
npm.cmd --prefix challenges/day-13-task-state start
```

Для настоящих ответов требуется серверная переменная `OPENAI_API_KEY`.
Используется `gpt-5.6-luna`; передаваемые контекст и расход видны в приложении.
Демонстрационный режим включается явно и не оценивает качество модели.

Первая команда проверяет код, типы и сборку без платных вызовов.
Вторая отдельно выполняет реальный эксперимент продолжения задачи:

```powershell
npm.cmd --prefix challenges/day-13-task-state run check
npm.cmd --prefix challenges/day-13-task-state run experiment:live
```

## Результаты и выводы

20 сентября 2026 года выполнены **3 реальных запроса к GPT-5.6 Luna**:
1314 входных + 108 выходных = **1422 токена**. Сценарий — подготовка
спецификации сервиса записи к репетиторам. Сохранён план: согласовать отмену,
описать бронирование, проверить требования. На каждом этапе явно заданы:

| Этап | Текущий шаг | Ожидаемое действие |
| --- | --- | --- |
| `planning` | Согласовать правило отмены | Уточнить отмену за 12 часов |
| `execution` | Описать проверку пересечения интервалов | Добавить запрет двойного бронирования в спецификацию |
| `validation` | Проверить отмену за 12 часов | Сопоставить правило отмены с критериями приёмки |

Задача ставилась на паузу и сохранялась в файлы. Новый экземпляр хранилища
`Repository` читал их, после чего пауза снималась. Это повторное чтение
в одном процессе, а не запуск двух процессов. Модель получала один запрос:
«Продолжи с места остановки. Верни только JSON: stage, step, expectedAction —
точные значения из актуального состояния задачи. Не проси заново объяснять
задачу». Все три обычных слоя памяти были выключены; состояние и профиль
подключались отдельно.

Совпали **9/9 значений**: три поля на каждом этапе. Пауза восстановлена
в **3/3 случаях**. Точные состояния в API-контексте, вопросы и ответы —
в [JSON-протоколе](results/live/results.json), итог —
в [отчёте](results/live/report.md), процедура —
в [исполнителе эксперимента](scripts/experiment.mjs).

Модель правильно воспроизвела сохранённое место остановки без повторного
перечисления условий в вопросе. Эта метрика проверяет чтение трёх полей,
а не способность самостоятельно закончить спецификацию или качество её
проверки. Условие отмены за 12 часов — учебные данные сценария.
Один короткий прогон не доказывает безошибочность будущих продолжений.
Повторная команда эксперимента заменяет файлы `results/live/`.

Прошли **39 локальных тестов**, включая паузу на всех четырёх этапах,
запрет действий на паузе, отдельное хранение и перезапуск HTTP-сервера.
Прошли проверка TypeScript и сборка. В браузере проверен полный цикл этапов,
включая паузу, перезагрузку страницы и продолжение сохранённой работы.

## Практическая польза

Явное состояние помогает возвращаться к длинной работе после перерыва,
передавать её другому исполнителю и видеть следующий шаг без чтения всей
переписки. Разделение этапа и паузы сохраняет место остановки, а отдельная
карточка делает прогресс проверяемым и понятным человеку.
