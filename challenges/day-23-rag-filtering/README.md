# День 23 — реранкинг, фильтрация и переписывание запроса

## Исходное задание

🔥 День 23. Реранкинг и фильтрация

Добавьте второй этап после поиска:

👉 reranker или фильтр релевантности (порог similarity / отдельная модель / heuristic)

Настройте:

👉 порог отсечения нерелевантных результатов
👉 топ-K до и после фильтрации

Сравните:

👉 качество без фильтра/rewriting
👉 качество с фильтром

Результат:

Улучшенный RAG: фильтрация/реранкинг + query rewrite + сравнение режимов

## Теория

**Двухэтапный поиск** отделяет широкий сбор кандидатов от выбора небольшого
контекста для ответа. На первом этапе важна полнота: не потерять потенциально
полезный фрагмент. На втором — точность: не передавать модели всё найденное.
Например, в справочнике учреждения сначала находятся двадцать упоминаний
«приёма», а затем отбираются правила записи посетителей, исключая приём товаров.

**Фильтрация** убирает результаты, нарушающие условие: слишком низкое сходство,
неподходящая версия документа, другой отдел или пустое содержание. Порог
сходства не универсален. Он зависит от модели, языка, корпуса и вида запросов.
Высокий порог уменьшает шум, но способен удалить единственный правильный ответ.
[Порог и ранжирование](https://developers.openai.com/api/docs/guides/retrieval).

**Реранкинг** меняет порядок уже найденных кандидатов. Это может быть отдельная
модель, которая совместно читает вопрос и фрагмент, или понятная эвристика.
Например, смысловое сходство можно дополнить совпадением технического термина.
Лексическое совпадение хорошо различает названия и коды, но хуже распознаёт
синонимы; семантический поиск помогает с синонимами, но может спутать номера
похожих документов. Сочетание этих сигналов требует проверки, а не веры в формулу.

**Query rewrite** — переписывание вопроса для поиска. Фраза «а где это хранится?»
без контекста почти бесполезна; самостоятельный запрос «место хранения отчётов
сервиса» конкретнее. При этом исходный вопрос остаётся задачей генератора.
Переписывание может потерять отрицание, номер версии или добавить неверное
предположение, поэтому преобразование нужно показывать и проверять. Дополнительный
вызов модели увеличивает время и расход; одинаковые преобразования можно кешировать.

```text
Вопрос → [переписывание] → 20 кандидатов → [фильтр + новый порядок] → 5 фрагментов
```

**Настройка и оценка** используют разные примеры. Если выбирать порог по тем же
вопросам, на которых потом объявляется качество, получится слишком оптимистичная
оценка. Для настройки нужны и вопросы с ответом, и посторонние. Для сравнения
нескольких улучшений полезны четыре режима: без них, только фильтр, только
переписывание, оба. Так виден вклад каждого компонента. Даже хороший реранкер
не достанет фрагмент, который не попал в исходный набор кандидатов.

## Решение

**Замысел.** Создать локальную лабораторию, где видны исходный вопрос, поисковая
переформулировка, кандидаты и причины отбрасывания. Пользователь меняет порог
и количество фрагментов, получает ответ либо сравнивает четыре режима. Проверяем
на одном корпусе и десяти вопросах, помогает ли более точный выбор доказательств.

**База.** Автономный [снимок 20 README](data/corpus.json), 18 628 слов,
две стратегии разбиения и настоящий [индекс](data/index.json.gz). Вопросы и
ожидания находятся отдельно в [questions.json](data/questions.json).
По умолчанию выбран структурный индекс: 170 фрагментов, до 1800 символов,
перекрытие 200 внутри длинного раздела, `text-embedding-3-small`, 512 измерений.

**Поиск.** В [retrieval.mjs](server/retrieval.mjs) реализованы четыре режима.
Базовый берёт первые пять из двадцати кандидатов. Фильтр исключает сходство ниже
0,30, фрагменты с менее чем 100 символами содержания без заголовков, точные
повторы и другой день, если номер явно указан в вопросе. Затем порядок меняется:
`0,65 × косинусное сходство + 0,35 × доля совпавших основ слов вопроса`.
Основа здесь — первые пять букв длинного слова, это простая эвристика, а не
морфологический анализатор. Имена источников и оценки остаются видимыми.

Переписывание делает `gpt-5.6-luna`, без эталонных ответов и без доступа к ним.
Если потерян явный номер дня или результат слишком длинный, используется
исходный вопрос. Это проверка сохранения номера, не доказательство полной
смысловой эквивалентности. Принятые переформулировки кешируются в базе дня.
Генератор ответа всегда получает исходный вопрос и отобранные документы.

Порог 0,30 выбран до итогового сравнения: из вариантов 0,20/0,30/0,40/0,50
это минимальное значение, исключившее оба посторонних калибровочных вопроса
при сохранении результатов двух профильных. Примеры — правила Дня 14,
подключение Дня 16, орбита спутника и луковый суп. Полные результаты настройки
сохранены в поле `calibration` протокола. Четыре примера — небольшая калибровка.

Нужен Node.js 22.13+. Из папки задания:

```powershell
npm.cmd ci              # установка зависимостей
npm.cmd start           # http://127.0.0.1:3023
npm.cmd run check       # тесты, типы и сборка без API
npm.cmd run experiment  # четыре режима × десять вопросов через API
```

Для новых запросов нужен серверный `OPENAI_API_KEY`. Остановка — Ctrl+C.
Данные — `~/.ai-tutors/rag-campaign` или общий для пяти сайтов `RAG_DATA_DIR`;
`day-23.sqlite` содержит состояние дня, `campaign.sqlite` — кеш и бюджет $1.
Сохранённый эксперимент просматривается без расходов. При неизвестном результате
API-вызова его резерв остаётся в журнале, автоматического повтора нет.

## Результаты и выводы

Реальные ответы и их точные входы сохраняет [протокол](results/experiment.json).
Серия 2026-10-05: 40 ответов и 10 переформулировок, плюс 10 новых эмбеддингов
запросов. 73 678 входных и 4618 выходных токенов, оценка $0,02389003.
Отдельная калибровка добавила 4 эмбеддинга, 87 токенов и $0,00000174.

| Режим | Текстовые маркеры | Смысл, 0–2 за вопрос |
| --- | ---: | ---: |
| Базовый | 15/26 | 12/20 |
| Фильтр и реранкинг | 24/26 | 19/20 |
| Только переписывание | 17/26 | 13/20 |
| Оба улучшения | 24/26 | 19/20 |

Смысловой разбор выполнен агентом по сохранённым ответам и исходным документам:
0 — нет ответа, 1 — частичный ответ или существенная неточность, 2 — полный.
В протоколе есть комментарий к каждой оценке. Это не независимая человеческая
экспертиза; один запуск не даёт статистической уверенности.

Отбор помог извлечь готовые профили, расписание и порядок инструментов.
Переписывание само по себе помогло расписанию, но не заменило фильтрацию.
Все режимы пропустили фрагмент с точными именами серверов Дня 20; в режиме
both модель дополнительно ошиблась в распределении расчёта сводки между ними.
Таким образом, поиск и фильтр повышают качество на этой выборке, но не
гарантируют полноту доказательств или отсутствие лишних выводов.

Прошли 12 локальных тестов, TypeScript и production-сборка.

Минимальные проверки и браузерные действия: [протокол проверки](results/verification.md).

## Практическая польза

Такой второй этап полезен для больших справочников с похожими страницами,
версиями и повторяющимися терминами. Наблюдаемый отбор помогает понять, почему
нужный факт не попал в ответ, а сравнение компонентов показывает, оправдывает
ли дополнительная модель затраты на переформулировку запроса.
