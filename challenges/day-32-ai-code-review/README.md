# День 32. Автоматизация ревью кода

Ассистент должен:

Автоматическое AI-ревью кода

## Теория

**Pull request (PR)** — предложение объединить изменения одной ветки с другой.
Ревью проверяет последствия этих изменений до слияния. Важен не только новый
текст, но и его отличие от предыдущей версии, соглашения проекта и окружающий
код. Например, удаление одного слагаемого в проверке лимита может нарушить
работу параллельных запросов, хотя функция продолжит проходить простые тесты.

**Diff** описывает добавленные и удалённые строки. Заголовок блока вида
`@@ -10,3 +10,4 @@` задаёт начальные номера и длины старого и нового диапазонов.
Номер строки в новой версии нельзя вычислить, просто считая строки diff:
удалённые строки не увеличивают новый номер. Для полезного замечания нужны
точный файл, существующая строка и объяснение воспроизводимого условия ошибки.
[Git: формат diff](https://git-scm.com/docs/diff-format).

**Контекст ревью** включает требования, архитектурные решения и вызывающий код.
RAG помогает найти относящиеся к изменению материалы, не передавая целый проект
в каждый запрос. При поиске по коду важно сохранять имена файлов и контекст
функций. Документация может устареть, поэтому противоречие между правилом и
реализацией нужно объяснить, а не скрывать за общими рекомендациями.

**AI-ревью** — вероятностная оценка, а не доказательство корректности. Модель
может заметить нарушение общего правила, но пропустить зависимость между
несколькими файлами или указать проблему, которая исключена контрактом вызова.
Полезное замечание содержит три части: что неверно, при каком входе это
проявится и почему предложенное исправление устраняет причину. Требовать
обязательный баг в каждой категории вредно: корректное изменение должно
допускать пустой список замечаний.

**Проверка ревьюера** использует изменения с заранее известными последствиями
и корректные изменения. Отдельно оценивают найденные реальные ошибки,
ложные замечания и корректность координат. Проверка JSON-структуры гарантирует
наличие полей, но не правильность анализа. Поэтому результаты автоматического
ревью дополняют тесты и оценку человеком, а не заменяют их.

**CI** (continuous integration, непрерывная интеграция) автоматически запускает
проверки при изменениях. GitHub Actions поддерживает события открытия PR,
обновления его ветки и повторного открытия.
[GitHub: события запуска](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).
Код из PR и команды в его документах являются недоверенными входными данными.
Процесс, имеющий API-ключ, не должен выполнять присланный код. Отчёт можно
сохранить как артефакт запуска, не предоставляя боту права писать в PR.
Для PR из внешнего форка обычные секреты не передаются исполнителю.
[GitHub: secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Решение

Замысел — использовать один механизм анализа и для наглядной локальной
страницы, и для автоматического запуска на PR. Человек выбирает контрольный
diff или изменения рабочего дерева, видит замечания и найденные материалы.
В CI тот же код получает два SHA коммитов, читает diff и версии изменённых
файлов, затем сохраняет Markdown/JSON. Проверять качество предполагается на
двух фиксированных изменениях: с ошибками и без намеренно внесённых ошибок.

Самостоятельное Node.js-приложение индексирует документацию AI Tutors и
исходники сервиса/бюджета. Облачные эмбеддинги, локальный поиск и Responses API
формируют структурированный отчёт. Веб-режим также добавляет небольшой явно
учебный документ с правилами контрольного примера; ожидаемые ответы в запрос
не передаются. Каждая позиция замечания сверяется с новой стороной diff.
Код PR не запускается, рабочие файлы не изменяются.

Из папки задания выполните:

```powershell
npm.cmd ci
npm.cmd start
```

Зависимости зафиксированы в lock-файле. Сайт доступен на
[127.0.0.1:3032](http://127.0.0.1:3032). Обновите базу знаний, выберите diff и
нажмите «Выполнить». Для новых вызовов нужен серверный `OPENAI_API_KEY`.
«Открыть сохранённый пример» работает без ключа. Остановка — Ctrl+C.
`npm.cmd run check` выполняет локальные проверки; `npm.cmd run experiment`
повторяет платную серию. Правила общего журнала $1 описаны в
[ADR серии](../../docs/decisions/0019-days-31-35-project-assistants.md).

Workflow находится в
[`.github/workflows/day-32-ai-review.yml`](../../.github/workflows/day-32-ai-review.yml).
Он запускается на `pull_request`, выполняет код доверенного base-коммита,
читает head как данные и формирует артефакт и Job Summary. После включения
workflow в основную ветку задайте `OPENAI_API_KEY` в GitHub Actions Secrets.
Первый PR, добавляющий сам инструмент, не может использовать отсутствующий
в base-коммите инструмент; полноценное применение начинается после включения.
Для форков предусмотрено явное сообщение о пропуске. Каждый CI-запуск имеет
собственный локальный журнал: он не ограничивает суммарные расходы будущих PR.

## Результаты и выводы

В [`data/reviews.json`](data/reviews.json) находятся точные diff и исходники
двух синтетических сценариев. В первом убрано `reserved` из проверки бюджета
и разрешён вход при отсутствующем ожидаемом токене; во втором изменено только
отображение стоимости. Реальные ответы модели сохраняются в
[`results/experiment.json`](results/experiment.json) и Markdown-отчётах.
Проверка от 2026-10-18: прошли все 7 локальных тестов и проверка синтаксиса.
Модель нашла обе внесённые ошибки на строках 2 и 5 первого diff. Во втором
diff выдала одно условное замечание о строковом входе `cost`: контракт типа
в примере не указан, поэтому отсутствие ошибок этим контролем не доказано.
Дополнительное утверждение модели о «падении» на NaN/Infinity неточно: метод
возвращает строки. Протокол сохраняет это замечание без исправления ответа.
Пример показывает необходимость ручной оценки и явных контрактов входов.
Затраты дня: 5 API-вызовов, расчётно $0,00276552, общий итог $0,01381912.

Серия на двух небольших diff не измеряет качество ревью произвольных PR.
Веб-режим рабочего дерева рассматривает только отслеживаемые разрешённые файлы.
CI ограничивает размер и число файлов, пропускает неподдерживаемые пути.
Проверка номера строки не доказывает наличие бага. Workflow подготовлен
локально; публикация и запуск настоящего GitHub PR в эту проверку не входят.

## Практическая польза

Инструмент даёт раннюю обратную связь по небольшим изменениям, связывает
замечания с проектными правилами и оставляет переносимый отчёт. Он полезен
перед ручным ревью, особенно для повторяющихся ошибок в лимитах, настройках
доступа и соблюдении архитектурных договорённостей.
