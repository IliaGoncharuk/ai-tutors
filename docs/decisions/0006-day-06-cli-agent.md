# Решение 0006: изолированный CLI-агент с памятью

- Статус: принято.
- Дата: 2026-09-10.
- Решение пользователя: «делай», после уточнения архитектуры и выбора CLI.

## Контекст

День 6 требует первого агента как отдельную сущность, инкапсулирующую обработку
входа и выхода, вызов LLM и память. Архитектура должна допускать создание многих
агентов с разными конфигурациями, но демонстрировать массовый запуск не нужно.
Вся переписка текущей сессии должна передаваться модели на каждом ходе.

## Рассмотренные варианты

1. Изолированный модуль `Agent` и интерактивный CLI — минимально показывает
   границу агента и не повторяет веб-инфраструктуру Дня 1.
2. REST-микросервис — сильнее изолирует процесс, но требует протокола сессий,
   HTTP-сервера и управления его жизненным циклом без пользы для критерия.
3. Расширение Дня 1 — уменьшает объём нового кода, но смешивает два учебных
   результата и создаёт риск регрессии завершённого задания.

## Решение

Выбран отдельный каталог с классом `Agent` и тонким CLI. Агент получает
LLM-клиент и конфигурацию при создании, применяет input/output policies, хранит
историю в памяти и отправляет полный диалог через Responses API с `store: false`.

Judge не добавляется: проверка качества или выбор кандидатов не входят в
условие, а LLM-judge создавал бы дополнительный платный вызов. Отдельная фабрика
массового создания тоже не нужна; независимый конструктор без глобального
состояния уже обеспечивает требуемую расширяемость.

## Последствия

- Граница между интерфейсом и агентом видна в коде и проверяется без API.
- Можно заменить CLI на REST или web, не меняя основной цикл агента.
- История разных экземпляров не смешивается.
- Размер и стоимость запроса растут с каждым ходом; ограничение контекста и
  compaction остаются будущим расширением.
- Перезапуск процесса удаляет историю, поскольку постоянное хранилище не входит
  в область Дня 6.
