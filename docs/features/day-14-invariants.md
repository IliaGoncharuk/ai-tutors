# День 14: проверяемые инварианты проекта

## Условие и границы

Дословное условие — в
[README Дня 14](../../challenges/day-14-invariants/README.md#исходное-задание).
Нужно хранить обязательные решения отдельно от диалога, учитывать их
в ответах и объяснять отказ при конфликтующем запросе.

Самостоятельное приложение находится в `challenges/day-14-invariants`,
работает на порту 3014 и не импортирует код других учебных каталогов.
Сохраняются профили, три слоя памяти и состояние задачи. Архитектурный выбор —
в [решении 0013](../decisions/0013-day-14-invariants.md).

## Набор правил

Правила относятся к проектируемому сервису записи к репетиторам:

| Поле | Обязательное значение |
| --- | --- |
| `architecture` | `монолит` |
| `frontend` | React |
| `backend` | Node.js |
| `storage` | SQLite |
| `lessonMinutes` | 45 минут |
| `cancellationHours` | 12 часов: отмена не позднее этого срока до начала, граница включена |

Это фиксированный учебный набор, привязанный к задаче. Изменение через
переписку, профиль или рабочую память не предусмотрено. Рабочие заметки
и предпочтения подачи не переопределяют обязательные значения.

Правила хранятся отдельно в `invariants.json` по задаче; принадлежность задачи
профилю сохраняет изоляцию. Каталог данных —
`~/.ai-tutors/memory-lab-day-14/`. Файл правил входит в публикуемую версию
вместе с памятью и `task-state.json`; `CURRENT.json` выбирает согласованный
набор. SQLite в таблице — решение для описываемого сервиса, локальное
хранилище лаборатории использует JSON.

## От запроса к принятому предложению

При обращении к модели в контекст включаются действующие правила,
состояние задачи, профиль и выбранные слои памяти. Ответ модели ограничен
JSON-схемой и содержит `kind`, `requestedChanges`, `design` и `topics`.
Модель определяет намерение и предлагает структуру; решение о допустимости
принимает код сервера.

`kind` различает совет, план, спецификацию, обзор и постороннюю тему.
`requestedChanges` содержит все шесть полей, с `null`, когда изменение
не запрошено. `design` содержит все шесть конкретных значений; лишние поля
и неверные типы отклоняются. В отправляемой модели JSON-схеме каждое поле
`design` имеет единственное допустимое значение из действующих правил
(`enum` из одного элемента). Значения `requestedChanges` остаются свободными
в рамках типов и длины, чтобы явно передать конфликтующую просьбу.
Строки ограничены 1–100 символами. Поддерживаемые темы: архитектура (`architecture`),
бронирование (`booking`), отмена (`cancellation`) и проверка (`validation`).

Сервер сопоставляет с инвариантами две части: явно запрошенные изменения
`requestedChanges` и проектное решение `design`. Поэтому отсутствие
изменения в списке не позволяет скрыть противоречащее значение в результате.
Несовпадение любого из шести полей отклоняет предложение.

Отказ формируется программой и показывает нарушенное правило и допустимое
значение. Успешный ответ также составляет программа из проверенных полей
и поддерживаемых тем; свободная проза модели не используется как текст
принятого решения. Профиль изменяет способ представления, сохраняя значения.

Для обычного совета выбирается один из шаблонов: таблица, если поле формата
содержит «Таблица»; нумерованный список, если стиль содержит «Кратко»;
иначе поясняющий текст с примером. План, спецификация, обзор и отказ имеют
собственные фиксированные формы. Произвольные пожелания профиля за пределами
этого выбора не гарантируются: в этой версии контроль правил важнее
свободного стилистического преобразования ответа.

Набор ограничен шестью полями и четырьмя темами. Такая проверка гарантирует
соблюдение перечисленных полей в принятом результате, но не является
универсальным анализатором естественного языка. Модель может пропустить
запрошенное изменение или ошибиться в намерении; итоговая проверка всё равно
не принимает `design` с запрещёнными значениями. Соответствие JSON-схеме
само по себе не считается соблюдением бизнес-правил.

## Прямые действия и материалы задачи

Форма проверки изменений обращается к `/api/proposal` и использует ту же
проверку без запроса к модели. Это позволяет отделить ошибку распознавания
намерения от ошибки правила сравнения.

План и спецификация создаются через генерацию текущего этапа и проходят
проверку предложения. Ручная запись произвольного текста в эти материалы
запрещена: иначе она обошла бы проверяемую структуру. Отклонённое предложение
не заменяет сохранённый план или спецификацию.

Состояния `planning`, `execution`, `validation`, `done`, пауза и продолжение
сохраняются. Сравнения памяти и профилей на паузе отклоняются до вызова API.
Текст обзора модели не становится свидетельством выполненных
программных тестов. Дополнительные условия одобрения плана и успешной
валидации для переходов в этом задании ещё не вводятся.

## Режимы и приёмка

В реальном режиме используется `gpt-5.6-luna` через Responses API,
ключ `OPENAI_API_KEY` берётся только сервером. Расход показывается по `usage`.
Демонстрационный режим помечен явно. `npm run check` выполняет локальные
проверки, `npm run experiment:live` — реальный учебный эксперимент.

Критерии приёмки:

1. Правила видны отдельно от переписки, сохраняются и передаются модели.
2. Рабочие сведения и профиль не могут заменить обязательные значения.
3. Конфликт выявляется и в `requestedChanges`, и в `design`; пользователь
   получает причину отказа и допустимый вариант.
4. Прямое предложение проверяется без API тем же правилом.
5. Итоговый текст формируется из проверенных данных; произвольная проза
   не обходит ограничения через чат, план или спецификацию.
6. Отклонённый результат не сохраняется как материал задачи.
7. Состояние, пауза, изоляция задач и профилей сохраняют своё поведение.
8. Проходят локальные проверки и интерфейсный сценарий; реальный эксперимент
   сохраняет вопросы, предложения, результаты проверки и расход.

Реальный сценарий содержит четыре независимых запроса из одного исходного
состояния: заменить Node.js на Django, увеличить занятие до 90 минут,
игнорировать правила и перейти на PostgreSQL, объяснить допустимое
бронирование и отмену. Проверяется ожидаемое разрешение или отказ, а при
конфликте — наличие конкретного нарушенного правила. Это проверка решения
по выбранным примерам, а не качества всех возможных формулировок.

[Исполнитель](../../challenges/day-14-invariants/scripts/experiment.mjs)
сохраняет вопрос, исходный ответ модели, структурированное предложение,
результат проверки, сформированный текст и расход в `results/live/results.json`.
Ошибки обработки включаются в протокол с доступным исходным ответом и `usage`.
Сумма охватывает доступные значения `usage`; если ответ от API не получен,
расход такой попытки по этому протоколу восстановить нельзя. Краткий отчёт —
в `results/live/report.md`; повторная серия заменяет эти файлы.

Итоговая и диагностическая серии, причина ложного отказа до уточнения схемы
и границы учёта расхода —
в [README](../../challenges/day-14-invariants/README.md#результаты-и-выводы).
