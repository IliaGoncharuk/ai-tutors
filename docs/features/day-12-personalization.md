# День 12: профиль и персонализация ассистента

## Условие и границы

Дословное условие — в
[README Дня 12](../../challenges/day-12-personalization/README.md#исходное-задание).
Требуется хранить профиль пользователя, подключать его к каждому запросу
и показать различие ответов для разных предпочтений.

Это самостоятельное локальное приложение в `challenges/day-12-personalization`
на порту 3012, без исполняемых импортов из других дней. Оно сохраняет три слоя
памяти и добавляет профиль поверх них. Архитектурное решение —
[0011](../decisions/0011-day-12-personalization.md).

## Профили и правила применения

Доступны три учебных профиля: `novice` — начинающий, `expert` — разработчик,
`manager` — руководитель. Пользователь выбирает профиль и редактирует его
уровень подготовки (`level`), стиль (`style`), формат (`format`)
и ограничения ответа (`restrictions`), а также отображаемое имя (`name`).
Актуальная версия сохраняется и применяется к последующим запросам.

Начальные настройки:

| Профиль | Уровень и стиль | Формат | Ограничения ответа |
| --- | --- | --- | --- |
| Начинающий | Первый проект; подробно, простыми словами, с объяснением терминов | Короткие абзацы и один бытовой пример | Без необъяснённых сокращений и кода |
| Разработчик | Опытный; кратко и технически точно, без вводных объяснений | Нумерованный список из трёх пунктов | Указать технические риски, без мотивационных фраз |
| Руководитель | Управление продуктом без технической специализации; деловая подача с акцентом на результат | Таблица «решение — польза — риск» | Без кода; явно указать критерий успеха |

Профиль добавляется в контекст автоматически, независимо от того, какие
обычные слои памяти включены. Отключение долговременных записей не отключает
персонализацию. Просмотр контекста показывает это различие явно.

Профиль задаёт предпочтения по умолчанию. Текущий вопрос может уточнить стиль
или формат конкретного ответа. Поле `restrictions` также относится к подаче,
а не к неотменяемым бизнес-правилам. Эта версия не содержит механизма жёстких
инвариантов; при его дальнейшем добавлении обязательные ограничения должны
иметь приоритет над предпочтениями. Поля профиля не разрешают менять системные
правила приложения и не служат исполняемыми инструкциями.

## Изоляция и хранение

Диалоги, задачи и персональные долговременные записи связаны с `profileId`.
В обычный запрос попадают только данные выбранного профиля. Переключение
выбирает последний созданный диалог этого профиля и связанную задачу;
если его ещё нет, создаёт пустую рабочую область. Попытка открыть диалог
другого профиля отклоняется. Переключение не копирует чужие данные.

Краткосрочная память хранит последние шесть сообщений диалога. Рабочая
содержит явные записи активной задачи, долговременная — сохранённые личные
сведения. Обычный ответ пополняет только диалог; перенос факта в другие слои
выполняется отдельным действием пользователя.

Каталог по умолчанию — `~/.ai-tutors/memory-lab-day-12/`.
Профили хранятся в разделе `profiles` файла `long-term.json`, личные записи —
в `entriesByProfile`. Диалоги —
в `sessions.json`, задачи — в `tasks.json`, служебный выбор и журнал —
в `system.json`. Согласованная версия раздельных документов публикуется
через `CURRENT.json`. Перезапуск восстанавливает текущую версию.

Это локальные открытые JSON-файлы без шифрования. Разделение профилей
внутри учебной программы не заменяет авторизацию многопользовательского
сервиса. Правила секретов и личных данных —
в [ограничениях проекта](../agent/CONSTRAINTS.md#публичность-и-чувствительные-данные).

## Сравнение профилей

Фиксируются вопрос, рабочие факты активной задачи и долговременные факты
активного профиля. Краткосрочный диалог исключается, чтобы он не задавал
предыдущую манеру ответа. Создаются три запроса с одинаковыми фактами
и вопросом; в каждом меняется только профиль предпочтений.

При таком сравнении память профилей `expert` и `manager` не читается для
подстановки в запрос активного `novice` и наоборот. Используются только
их настройки подачи и один выбранный набор фактов. Ответы не добавляются
в диалог и не становятся входом для следующего варианта.

Проверяется фактический профиль в каждом запросе, различие подачи и
сохранение общих исходных фактов. Нельзя оценивать персонализацию только
по тому, что ответ перечислил настройки: содержание объяснения должно
соответствовать им.

В реальном сценарии вопрос касается отмены занятия и защиты от двойного
бронирования. Исходные данные — учебный пример сервиса записи к репетиторам:
занятие 45 минут, веб-приложение, русский язык и `Asia/Yekaterinburg`.
[scripts/experiment.mjs](../../challenges/day-12-personalization/scripts/experiment.mjs)
ищет простые признаки: слово про пример для начинающего, три нумерованных
пункта для разработчика и строку таблицы для руководителя. Отдельно фиксируется
отсутствие Markdown-блоков кода. Эти эвристики не оценивают понятность,
корректность рекомендаций или все предпочтения; ответы дополнительно читаются.

Точные входы и ответы сохраняются в `results/live/results.json`, человекочитаемый
отчёт — в `results/live/report.md`; повторный запуск заменяет файлы.
Результаты серии 20 сентября и содержательные ограничения метрики —
в [README](../../challenges/day-12-personalization/README.md#результаты-и-выводы).

## API и режимы

Используются Responses API и `gpt-5.6-luna`. Ключ `OPENAI_API_KEY` доступен
только серверу. Реальный режим отправляет вопрос, профиль и выбранные
данные памяти OpenAI; сайт показывает расход по `usage`. Персонализация
передаётся заново в каждом запросе; поведение API описано в
[документации инструкций](https://developers.openai.com/api/docs/guides/prompt-engineering#message-roles-and-instruction-following).

Демонстрационный режим включается явно и помечается как симуляция.
Ошибка API не должна подменяться демонстрационным ответом.
`npm run experiment:live` выполняет три платных запроса на вымышленных данных.
Команды запуска, статус проверок и результаты — в README задания.

## Приёмка

1. Пользователь видит и может отредактировать все четыре поля профиля.
2. Профиль автоматически присутствует в каждом запросе, в том числе
   при отключении всех обычных слоёв памяти.
3. Профили имеют изолированные диалоги, задачи и личные долговременные записи.
4. Редактирование и выбор профиля сохраняются после перезапуска.
5. Сравнение делает три независимых запроса с одинаковыми фактами,
   разными профилями и без краткосрочной памяти; диалог не меняется.
6. Текущий запрос может уточнять предпочтения; они не представлены
   как гарантированный механизм запрета действий.
7. Проходят локальные тесты, проверка типов, сборка и проверка интерфейса;
   реальный эксперимент сохраняет точные входы, ответы и расход.
